1. 一句话定义当前项目状态

面试里一个非常关键的能力，是能把“当前阶段到底完成到哪里”讲得既准确又不过度。

推荐表述：
这是一个面向网络安全知识资料的 RAG 后端项目，当前已经完成到 Phase 4。系统不仅能接收文档、完成解析与基础清洗，还已经能把法规、标准、教材、手册和普通文本切成结构化 chunk，建立 parent-child 关系，生成稳定的 chunk_hash，并把 chunk 数据落到 PostgreSQL 中。但当前仍未进入 embedding、向量索引、关键词索引和检索问答阶段。

4. 切分链路怎么讲清楚

真正体现理解深度的，不是“我做了 chunking”，而是你能把结构化切分讲成一个完整闭环。

推荐你背下来的处理顺序

客户端上传文件
  -> upload_service 保存原始文件并创建 document/version/task
  -> worker 收到 ingest_document_task
  -> parser_service 解析原始文件
  -> cleaner_service 做基础清洗
  -> chunk_service 按 doc_type 选择 chunker
  -> 生成 parent / child chunk
  -> 规范化文本并生成 chunk_hash
  -> build_chunk_records 映射为 ORM 可落库记录
  -> 写入 PostgreSQL chunks 表
  -> 更新 ingest_task 状态

为什么 Phase 4 很关键

因为从这一阶段开始，系统第一次拥有了“后续可检索、可引用、可增量更新”的结构化知识单元。没有 Phase 4，后面的 embedding 和检索都没有稳定输入对象。

为什么 parent-child 现在就必须做

因为后续检索和答案生成对上下文的需求不同：child 需要更细粒度、适合检索；parent 需要更大上下文、适合答案回填。所以现在不只是“切成很多块”，而是要从现在开始建立两层结构。

5. 关键设计点为什么这样做

面试里最常见的追问，几乎都在“为什么”上。

1）为什么 law / standard 和 textbook / manual 要分开切？

因为它们的组织方式完全不同。法规和标准通常是章/节/条的结构；教材和手册更像标题层级 + 段落/代码块。强行用同一个切分器，metadata 会变得非常混乱，也很难解释。

2）为什么 fallback recursive chunker 仍然需要？

因为真实文档并不总是结构清晰。TXT 可能没有标题，PDF 结构可能抽取不稳定。如果没有兜底策略，系统会在“结构识别失败”时直接失去可用 chunk 输出。

3）为什么 child chunk 必须保留 article_no？

因为后续检索命中 child 时，引用链路仍然需要回答“这是哪一条”。如果拆分后 article_no 丢了，法规类场景的可解释性会大幅下降。

4）为什么 chunk_hash 基于 normalized_text 而不是原始 text？

因为原始 text 容易受到换行、空格、格式差异影响。用 normalized_text 可以降低无意义格式波动对 hash 的干扰，同时保留对真实内容变化的敏感性，这对后续 chunk diff 非常重要。

5）为什么现在只落 PostgreSQL，不直接上 Qdrant？

因为 Phase 4 的职责边界就是“把文本变成结构化 chunk 并落库”。如果现在顺手把 embedding、Qdrant 或 FTS 也做了，就会直接越界进入 Phase 5/6。

6）为什么当前任务完成不等于“系统已经能检索”？

因为现在完成的只是解析、清洗、切分和 chunk 落库。后面还缺 embedding、向量索引、关键词索引、融合排序和查询接口。所以当前完成只能理解为“Phase 4 阶段目标完成”。

6. 面试官高频追问与答题思路

下面这些问题，就是你讲到当前阶段时大概率会被追问的点。

Q1：你们现在的 chunk 是怎么切的？
A：不是单一策略。法规/标准优先按章节条切，教材/手册优先按标题层级和段落切，结构不清晰时走 fallback recursive chunker。这样可以让 chunk 规则更贴近文档本身的语义结构。
Q2：为什么要设计 parent-child 两层？
A：因为后续检索和回答阶段对上下文粒度要求不同。child 更适合细粒度召回，parent 更适合命中后的上下文回填。如果现在不分层，后续很难同时兼顾召回精度和答案上下文完整性。
Q3：为什么 chunk_hash 在现在这个阶段就做？
A：因为后续增量更新和 chunk diff 必须依赖稳定内容指纹。Phase 4 正好是首次正式生成 chunk 的阶段，所以最合理的时机就是现在。
Q4：如果章节/条款识别不到怎么办？
A：当前策略是不猜测、不伪造。识别不到时就降级为 fallback chunking，同时把 chapter/section/article_no 保持为 null，这样虽然信息少一些，但语义上更可靠。
Q5：你们现在的 chunk 已经可检索了吗？
A：还不行。现在 chunk 只是落在 PostgreSQL 里，embedding、Qdrant、FTS 和 retrieval 逻辑都还没做，所以只能说“结构化数据准备好了”，不能说“检索链路完成了”。
Q6：worker 为什么要在这个阶段就负责 chunk 落库？
A：因为从系统流程看，上传后的异步处理链路本来就应该承担后续 ingest 阶段工作。Phase 4 只是把 worker 从“解析/清洗入口”继续推进到“切分并落库”，这符合分阶段演进方式，也保证了主链路的一致性。

9. 你该怎么口述这个项目

最后给你一个适合面试场景的口述模板。

我做的是一个网络安全领域 RAG 知识库后端项目。这个项目是按 Phase 逐步推进的：先完成工程骨架和基础设施联通，再完成数据库地基、上传入口、解析与清洗。当前推进到 Phase 4，核心是把可解析的文本变成结构化 chunk 数据。现在系统已经能针对法规、标准、教材和普通文本采用不同切分策略，生成 parent-child 两层 chunk，保留页码和章节/条款等 metadata，并基于 normalized_text 生成稳定的 chunk_hash，最后把 chunk 落到 PostgreSQL 里。这样虽然还没有进入向量索引和检索阶段，但已经把后续检索系统最关键的数据层准备好了。
