4. 上传链路怎么讲清楚

真正能体现你理解深度的，不是“我做了上传接口”，而是你能把链路讲成一个完整闭环。

推荐你背下来的处理顺序

客户端上传文件
  -> FastAPI route 接收 multipart/form-data
  -> upload_service 读取文件 bytes
  -> 校验文件名 / 扩展名 / MIME / 大小
  -> 计算 SHA-256 file_hash
  -> 预生成 document_id / version_id / task_id
  -> storage_service 保存原始文件
  -> 单次事务创建：document + document_version + ingest_task
  -> commit 成功后 dispatch Celery 任务
  -> 返回 document_id / version_id / task_id / status=queued

为什么这是一个“最小闭环”

虽然当前还没有真正把文档内容解析成 chunk，但系统已经具备了“接收到文档 -> 固化为可追踪实体 -> 投递异步处理入口”的完整起点。这个起点是后续所有 ingest pipeline 的前置条件。

上传成功后数据库里会出现什么

  • documents： 逻辑文档主体
  • document_versions： 当前上传生成的第一个版本，version_no = 1
  • ingest_tasks： 当前上传对应的异步任务记录，初始状态为 queued

5. 关键设计点为什么这样做

这一节是面试最容易被追问的“为什么”。

1）为什么 upload 不能传 document_id？

因为规格把语义切得很清楚：upload 只负责创建新文档，而不是给已有文档加版本。已有文档产生新版本应由后续 replace 流程负责。这样可以避免一个接口同时承担“新建”和“更新”两套业务语义。

2）为什么文件存储路径要按 document/version 分层？

因为原始文件未来要支持版本演进、审计追踪、失败清理和 diff 对比。如果只用原始文件名，很容易冲突，也无法快速定位“某个 document 的某个 version 的原始文件在哪里”。

3）为什么先存文件，再写数据库？

因为数据库里的 storage_path 需要指向真实已存在的文件。如果反过来先写 DB，再发现文件写失败，就会留下不可用记录。当然这样做会带来另一个问题：如果 DB 提交失败，文件会残留。所以当前实现里又补了回滚清理逻辑，尽量删除刚写入的文件。

4）为什么 document / version / task 要放在同一个事务里？

因为这三者在业务上是一组原子结果。只成功其中一部分会导致系统进入不一致状态，比如有版本没有文档，或有任务没有版本。

5）为什么 Celery dispatch 放在 commit 之后？

因为如果任务已经发出，但数据库事务还没落地，worker 可能先读取任务却找不到对应记录，造成时序问题。先 commit 再 dispatch，可以保证 worker 拿到的是已持久化状态。

6）为什么当前 worker 只做占位，不直接开始解析？

因为规格要求严格按 Phase 推进。Phase 2 只负责把异步入口接起来，不允许偷跑到 Phase 3/4/5 的解析、chunk、embedding、索引逻辑。这样可以保证每个阶段的交付边界清晰、测试范围稳定。

6. 面试官高频追问与答题思路

下面这些问题，几乎就是你在讲项目时最容易被追问的点。

Q1：你们当前的上传接口已经完成到什么程度？
A：已经完成了接收 multipart/form-data、校验文件、计算 SHA-256、将原始文件保存到本地存储、创建 document/document_version/ingest_task 记录，并投递 Celery 异步任务入口。真正的解析、切分和索引尚未在这个阶段实现。
Q2：为什么要单独引入 ingest_task 表，而不是只改 document 状态？
A：因为“文档实体”和“异步处理任务”是两个维度。一个 document 未来可能经历多次 replace、reindex 或失败重试，任务状态需要独立持久化和审计，不能把任务生命周期揉进 documents 表里。
Q3：为什么 file_hash 在 Phase 2 就做了？
A：因为 file_hash 是后续版本管理、重复文件识别、增量更新和审计追踪的重要基础字段。虽然当前还没做 diff，但把内容指纹先固化下来是合理且低耦合的准备工作。
Q4：你们为什么把 route 写得很薄？
A：这是典型的分层设计。route 只负责 HTTP 协议层解析与错误映射，真正业务编排放在 service。这样更利于测试、复用和后续扩展，也避免 API 层和业务逻辑耦合。
Q5：如果数据库提交失败了，但文件已经落盘了怎么办？
A：当前实现里在异常分支会 rollback 数据库事务，并尝试删除已经保存的文件，减少脏数据残留。这体现的是“文件系统与数据库不是天然原子一致”的工程意识。
Q6：那你们现在能检索上传的文档了吗？
A：还不能。当前只能把上传动作固化下来，并投递异步入口。真正进入可检索状态，要等后续 Phase 把解析、chunk、embedding、索引、检索链路补齐。
