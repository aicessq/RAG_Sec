1. 一句话认识当前项目

先学会用一句准确的话定义项目当前状态，这在面试里非常重要。

推荐表述：
这是一个面向网络安全知识管理与检索的 RAG 系统项目，但当前仓库只完成了 Phase 0 基础工程搭建：包括 FastAPI 后端骨架、PostgreSQL/Redis/Qdrant 基础设施编排、配置系统、健康检查接口和基础测试；真正的上传、解析、切分、检索、生成、增量更新等 RAG 业务逻辑还没有开始实现。

这句话的好处是：

  • 不夸大当前完成度；
  • 能体现你知道项目边界；
  • 面试官会觉得你对工程状态有清晰判断。

2. Phase 0 到底完成了什么

不要笼统说“搭了个框架”，要能拆成面试官能继续追问的几个点。

工程骨架 已完成

目录结构、模块分层、后端包布局、测试目录、模型目录、Docker 相关文件都已建立。

FastAPI 应用入口 已完成

应用可启动，路由可注册，异常兜底已建立，根路径健康检查已可用。

基础设施联通 已完成

Docker Compose 可拉起 PostgreSQL、Redis、Qdrant、backend，并通过健康检查管理依赖顺序。

配置系统 已完成

使用 pydantic-settings 统一读取环境变量，并生成数据库/缓存/向量库连接串。

健康检查接口 已完成

已实现 /health 和 /api/v1/health/ready，区分存活探针与就绪探针。

测试基础 已完成

已区分默认测试和 integration 集成测试，能验证启动层和依赖联通性。

Phase 0 的本质

当前阶段不是为了“把 RAG 做出来”，而是为了先把后续开发所依赖的工程地基打稳。也就是说，这一阶段更像是在解决：

  • 项目如何组织；
  • 服务如何启动；
  • 基础设施如何连接；
  • 代码以后往哪里扩展；
  • 出了问题如何快速排查。

3. 当前架构怎么理解

面试官很喜欢问“你这个项目的结构是怎么分层的？为什么这么分？”

3.1 当前已经跑起来的主链路

客户端请求
   ↓
FastAPI app (backend/app/main.py)
   ↓
API Router 聚合 (backend/app/api/__init__.py)
   ↓
health 路由 (backend/app/api/health.py)
   ↓
依赖检查
   ├─ PostgreSQL: backend/app/db/session.py
   ├─ Redis:      backend/app/dependencies.py
   └─ Qdrant:     backend/app/dependencies.py

3.2 为什么这样分层

层 职责 当前代表文件
入口层 创建应用、初始化日志、注册路由、全局异常兜底 backend/app/main.py
路由层 定义 HTTP 接口，不放复杂业务逻辑 backend/app/api/health.py
依赖层 集中管理 Redis / Qdrant / DB 会话等基础依赖 backend/app/dependencies.py
数据库层 负责引擎、会话工厂、连通性检查 backend/app/db/session.py
配置层 统一读取环境变量并派生连接串 backend/app/config.py
你要学会说：
我们当前虽然只实现了健康检查，但已经按照未来 RAG 系统的完整分层方式组织代码，目的是避免后续把解析、切分、检索、生成逻辑写进路由层，导致结构失控。

4. 已实现模块逐项拆解

这里是“项目细节题”的准备区，面试官会从这些点往下问。

4.1 main.py 做了什么

  • 创建 FastAPI 应用；
  • 在应用创建前初始化日志；
  • 挂载 /api/v1 业务路由；
  • 单独保留根路径 /health；
  • 注册统一异常兜底，避免直接暴露堆栈。
面试官可能会问：为什么 /health 不放在 /api/v1 下？
因为存活探针通常是最基础、最稳定的系统级接口，容器编排和外部探活经常直接依赖它。当前实现把它保留在根路径，是为了符合最简单的探活约定，也符合规格要求。

4.2 config.py 做了什么

  • 用 BaseSettings 统一管理配置；
  • 定义了 PostgreSQL / Redis / Qdrant 的基础连接字段；
  • 通过属性动态生成 postgres_dsn、redis_url、qdrant_url；
  • 通过 lru_cache 缓存配置对象。
面试官可能会问：为什么不用一个字符串直接写死连接串，而是拆字段再拼装？
因为拆字段更利于本地开发、Docker、生产环境切换，也更方便做类型校验。比如 host、port、db、user 分开管理后，配置更清晰，错误更早暴露。

4.3 db/session.py 做了什么

  • 创建 SQLAlchemy 引擎；
  • 创建 SessionLocal；
  • 通过 SELECT 1 实现数据库连通性检查；
  • 使用 pool_pre_ping 和 pool_recycle 提高连接可靠性。
面试官可能会问：为什么 Phase 0 还没有 ORM 表，但已经建了数据库会话工厂？
因为 Phase 0 的目标之一就是验证数据库连接是可用的，同时为后续模型和接口预留统一的访问入口。提前把基础设施打通，可以降低后面 Phase 的调试成本。

4.4 dependencies.py 做了什么

  • 集中创建 Redis 客户端；
  • 懒加载 Qdrant 客户端；
  • 封装 Redis / Qdrant 连通性检查；
  • 提供未来接口可复用的 get_db() 依赖。
面试官可能会问：为什么 Qdrant 客户端要懒加载？
因为当前阶段很多开发和测试场景下 Qdrant 可能并没有启动。懒加载能减少导入时副作用，也方便后续测试时替换 mock。

4.5 健康检查为什么要分两层

接口 用途 是否依赖外部服务
/health 看进程是不是活着 否
/api/v1/health/ready 看系统是否已具备接收真实流量的条件 是，需要检查 PG/Redis/Qdrant
面试官可能会问：为什么某个组件挂了，/health/ready 不是直接返回 500？
因为 readiness 的核心是“告诉你当前哪些依赖没准备好”，而不是简单抛错。当前设计返回结构化状态，便于脚本、运维、测试直接看到 PostgreSQL、Redis、Qdrant 分别出了什么情况。

5. 面试官高频问题与回答思路

下面这些问题，是你几乎一定会被追问到的。

Q1：这个项目现在到底做到了哪一步？
目前只完成了 Phase 0。也就是工程基础搭建已经完成，服务能启动、基础设施能连接、健康检查和测试基础已建立，但文档上传、解析、切分、检索、生成这些 RAG 业务还没有开始实现。
Q2：为什么一开始没有直接做 RAG 逻辑？
因为 RAG 项目依赖很多基础设施：数据库、缓存、向量库、配置、任务机制。如果这些底层没有先打通，后面写上传、解析、索引、检索时会把问题混在一起，很难调试。Phase 0 的价值就是先把工程地基打稳。
Q3：为什么当前目录里已经有很多 services/models/workers 文件，但你说它们还没实现？
因为这个项目是按完整目标架构先铺目录，再按 Phase 顺序逐步填实现。这样做的好处是后续模块挂载位置清晰，但也要求我们不要把“文件存在”误解成“功能已经实现”。
Q4：你觉得当前最有价值的实现点是什么？
不是某个接口，而是“工程约束已经被建立起来了”：配置统一、分层清晰、依赖集中管理、健康检查可观测、测试具备分层。这些会决定后续项目能不能可持续扩展。
Q5：当前测试策略体现了什么工程思路？
体现了“把不依赖基础设施的测试和依赖真实服务的测试分开”。默认 pytest 保证轻量快速，integration 测试显式开启，用来做联通性和环境验收。这是比较典型的工程分层测试方式。
Q6：为什么当前要用 PostgreSQL + Redis + Qdrant 这三个组件？
从项目定位看：PostgreSQL 负责结构化持久化，Redis 适合做实时任务状态缓存，Qdrant 适合做向量检索。虽然业务还没实现，但基础设施已经按未来职责拆好了。
Q7：如果面试官问“你这个项目的难点在哪”，在 Phase 0 应该怎么答？
Phase 0 的难点不在业务算法，而在工程边界控制：要保证当前阶段只做基础设施和骨架，不提前写超范围的业务逻辑；同时又要把未来扩展路径提前设计清楚，让后续每一层都能自然接上。

6. 你需要会的运行与验证命令

如果面试官问“你怎么证明它现在是能跑的”，你至少要会这些命令。

6.1 安装依赖

python -m venv .venv
pip install -e ".[test]"

6.2 本地启动后端

cd backend
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000

6.3 Docker Compose 启动

cp .env.example .env
docker compose up -d --build
docker compose logs -f backend

6.4 验证接口

curl http://localhost:8000/health
curl http://localhost:8000/api/v1/health/ready

6.5 跑测试

pytest
pytest -m integration
pytest backend/tests/test_health.py::test_health_returns_ok
你要会解释：
pytest 默认不会跑 integration 测试，因为项目配置里已经把 -m 'not integration' 设为默认行为了。这样即使没有起 PostgreSQL/Redis/Qdrant，默认测试也不会全部报红。

8. 你可以怎么讲这个项目

下面这段适合你在面试中直接口述，或者稍作修改后用于答辩。

推荐讲法：

这个项目是一个面向网络安全知识库场景的 RAG 系统，但我目前完成的是 Phase 0，也就是工程初始化阶段。现阶段我主要做了三件事：第一，搭建了 FastAPI 后端骨架和清晰的模块分层；第二，用 Docker Compose 把 PostgreSQL、Redis、Qdrant 和后端服务编排起来，并建立了健康检查与就绪检查；第三，补上了配置系统和分层测试，让项目具备可启动、可联通、可验证的基础。

当前还没有进入真正的 RAG 业务链路，比如文档上传、解析、chunk 切分、embedding、检索融合、答案生成这些能力都还没实现。但我已经把这些模块的目录和边界提前设计好了，这样后续可以按阶段逐步落地，而不会把业务逻辑堆到路由层或把依赖初始化写乱。

你在这一阶段最该体现的能力

  • 不是“算法做了多少”，而是“工程基础打得是否扎实”；
  • 不是“功能看起来多不多”，而是“边界是否清晰、结构是否可扩展”；
  • 不是“会不会吹项目”，而是“能不能准确说明已经完成和未完成的内容”。
