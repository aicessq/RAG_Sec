1. 一句话定义当前项目状态

先学会用一句准确的话讲项目当前阶段，这是面试里最重要的基本功。

推荐表述：
这是一个面向网络安全知识管理与检索的 RAG 系统项目，当前已经从 Phase 0 的工程骨架阶段推进到 Phase 1。现阶段已经完成 PostgreSQL ORM 数据模型、Alembic 迁移基础、首个数据库 schema、最小 CRUD 辅助层以及数据库相关测试骨架，但还没有进入文件上传、文本解析、chunk 切分、向量索引、检索融合和答案生成这些 RAG 业务流程。

2. Phase 1 相比 Phase 0 升级了什么

面试官会关心你不是“写了更多文件”，而是“系统能力发生了什么升级”。

Phase 0 已完成

解决的是：服务能不能启动、基础设施能不能连、项目结构是否清晰。

Phase 1 已完成到当前实现

解决的是：系统有没有正式的持久化地基，后续业务是否有可依赖的数据模型和迁移机制。

本质变化

  • 从“只有数据库连接检查”升级为“有正式 ORM 表结构”；
  • 从“只有工程骨架”升级为“具备 schema migration 能力”；
  • 从“无法验证真实持久化”升级为“可以创建核心数据库对象并进行最小 CRUD 验证”。

4. 你要理解的数据库设计重点

面试官很喜欢问“你数据库是怎么设计的，为什么这么设计”。

4.1 为什么要先做这些表

表 作用 为什么 Phase 1 就要做
documents 逻辑文档主记录 后续上传、版本切换、检索可见性都依赖它
document_versions 文档历史版本 后续 replace 和增量更新必须依赖版本建模
chunks chunk 存储与检索基础 后续切分、索引、检索都要落到这里
ingest_tasks 入库/替换任务持久化 后续 Celery 任务状态需要 Redis + DB 双写
query_logs / feedback 查询审计与用户反馈 后续安全、效果分析、可观测性都要靠它们
eval_* 评测数据集与运行结果 规格中已提前约定，Phase 1 要先把地基打好

4.2 设计上的几个关键点

  • 主键统一 UUID：便于分布式生成与后续数据扩展；
  • JSONB 字段有默认值：避免空值和 Python 可变对象默认值混乱；
  • 只用 VARCHAR + 应用层枚举约束：当前阶段不引入 PostgreSQL ENUM 迁移复杂度；
  • chunks 保留 search_tsv：虽然 FTS 逻辑没做，但表结构先定义好；
  • documents.current_version_id 与 document_versions 存在循环依赖：迁移要分步建立外键。
你可以这样解释：
Phase 1 不做业务流程，但必须把后续上传、版本管理、切分、检索、评测会依赖的数据结构一次性定义清楚，否则后面每个 Phase 都会反复返工 schema。

5. 当前代码结构怎么讲

面试官会继续追问：你这些数据库能力是怎么挂进现有项目结构里的？

config.py
  ↓
db/session.py        —— 统一 engine / SessionLocal
  ↓
db/base.py           —— 统一 DeclarativeBase / metadata
  ↓
models/*.py          —— 定义 10 张核心表的 ORM 结构
  ↓
alembic/env.py       —— 复用 Settings + Base.metadata
  ↓
alembic/versions/*   —— 首个 schema migration
  ↓
services/crud_service.py —— Phase 1 最小 CRUD 辅助层
  ↓
tests/conftest.py + test_models.py + test_crud.py

为什么不直接在路由里写 CRUD？

因为当前阶段的重点是“先把持久化基础做好”，不是马上做业务 API。把最小 CRUD 放在服务辅助层，可以：

  • 先验证模型与事务是可用的；
  • 避免为了演示接口而提前越过 Phase 边界；
  • 给后续真正的业务 API 预留更稳定的复用点。

6. 面试官高频追问与答题思路

以下问题，是你在讲到 Phase 1 时大概率会被追问的。

Q1：你为什么在还没做上传和检索之前，就先做这么多数据库表？
因为这些表不是“以后可能用到”，而是后续所有 Phase 的正式依赖。比如没有 document_versions，就没法做 replace；没有 chunks，就没法做切分结果持久化；没有 ingest_tasks，就没法做异步任务审计。Phase 1 的核心就是把持久化地基一次性铺好。
Q2：为什么用 Alembic，而不是直接手写 SQL？
因为这个项目后续会持续演进 schema，单靠手写 SQL 不利于版本管理、升级回滚和团队协作。Alembic 可以让 ORM 模型和数据库 schema 有统一的演进路径。
Q3：Phase 1 里最容易出错的地方是什么？
主要有三个：第一，JSONB 默认值既要考虑 Python 侧 default，也要考虑数据库侧 server_default；第二，documents 和 document_versions 存在循环依赖；第三，chunks 里的 search_tsv、GIN 索引和 JSONB 字段都依赖 PostgreSQL 方言，不能偷懒退回普通类型。
Q4：为什么当前只做“最小 CRUD 辅助层”，而不是完整 REST API？
因为规格明确要求 Phase 1 不要提前做上传、解析、查询等业务逻辑。当前最小 CRUD 的目的只是验证模型、事务和持久化链路通了，而不是对外暴露完整业务能力。
Q5：为什么 chunks 表在 Phase 1 就要有 search_tsv 字段？
因为 PostgreSQL FTS 是后续架构确定的一部分。即使检索逻辑还没实现，schema 也应该先定义好，避免后面再做破坏性迁移。
Q6：你现在真的实现了“RAG”吗？
严格说还没有。当前只是把 RAG 所依赖的数据结构、迁移机制和最小持久化能力建立起来了。真正的 RAG 业务链路要在后续 Phase 才实现。

7. 你需要会的运行与验证命令

如果面试官问“你怎么证明这部分是能工作的”，至少要会这些命令。

7.1 安装依赖

pip install -e ".[test]"

7.2 启动数据库相关基础设施

docker compose up -d postgres redis qdrant

7.3 执行迁移

cd backend
alembic upgrade head

7.4 跑默认测试

pytest

7.5 跑数据库相关测试

pytest -m integration
pytest backend/tests/test_models.py backend/tests/test_crud.py -m integration
注意：
当前测试仍然保持分层：默认 pytest 不跑 integration；数据库相关测试只在你明确启动 PostgreSQL 并显式运行 integration 标记时才执行。

9. 你该怎么口述这个项目

下面这段话适合你在面试或答辩时直接使用。

推荐讲法：

这个项目是一个面向网络安全知识库场景的 RAG 系统。我目前已经把项目从 Phase 0 推进到 Phase 1。Phase 0 主要完成了工程骨架、基础设施编排和健康检查；Phase 1 则重点补齐了正式的持久化地基，包括 PostgreSQL ORM 模型、Alembic 迁移能力、首个数据库 schema，以及最小 CRUD 辅助层和数据库测试骨架。

我这样分阶段推进，是因为后续上传、版本管理、chunk 切分、向量索引、检索和评测都会依赖稳定的数据结构。如果一开始就直接写 RAG 业务，而 schema 还没定好，后面会反复返工。现在虽然还没有实现完整 RAG 流程，但项目已经具备了正式的数据持久化基础，后续 Phase 可以在这个基础上逐层扩展。

你在 Phase 1 最应该体现的能力

  • 你理解“先做工程地基，再做业务流程”的节奏控制；
  • 你知道如何把数据库模型、迁移、约束、索引一次性规划好；
  • 你能准确区分“已经完成的持久化基础”和“尚未开始的 RAG 业务能力”。

本文档基于当前仓库中的实际代码、Phase 1 计划、README 与规格文档整理。适合学习和复盘，不建议把未实现的后续能力包装成当前成果。
