1. 一句话定义当前项目状态

面试里一个非常关键的能力，是能把“当前阶段到底完成到哪里”讲得既准确又不过度。

推荐表述：
这是一个面向网络安全知识资料的 RAG 后端项目，当前已经完成到 Phase 5。系统不仅能接收文档、完成解析、清洗、结构化切分与 chunk 落库，还已经能对 child chunk 生成本地 embedding、写入 Qdrant、更新 PostgreSQL FTS 字段，并统一组织后续检索所需的 metadata payload。但当前仍未进入查询接口、混合召回、RRF 融合和答案生成阶段。

2. Phase 5 相比 Phase 4 升级了什么

面试官更关注“系统能力发生了什么本质变化”，而不仅仅是“你多写了几个 service”。

Phase 3 已完成

解决文件解析、页码保留、基础清洗和失败状态回写问题。

Phase 4 已完成

解决结构化切分、parent-child 关系、chunk_hash 和 chunk 落库问题。

Phase 5 当前重点

解决“数据库里的 child chunk 如何真正变成检索系统可用索引数据”问题。

本质升级

  • 系统从“只有结构化 chunk 数据”升级为“已经具备可检索索引数据”。
  • worker 不再止步于 chunk 落库，而是继续完成 embedding、Qdrant 和 FTS 建立。
  • Phase 6 的 retrieval 终于有了真实可用的底层索引输入。

4. 建索引链路怎么讲清楚

真正体现理解深度的，不是“我做了 embedding”，而是你能把索引建立讲成一个完整闭环。

推荐你背下来的处理顺序

客户端上传文件
  -> upload_service 保存原始文件并创建 document/version/task
  -> worker 收到 ingest_document_task
  -> parser_service 解析原始文件
  -> cleaner_service 做基础清洗
  -> chunk_service 按 doc_type 选择 chunker
  -> 生成 parent / child chunk
  -> build_chunk_records 映射为 ORM 可落库记录
  -> 写入 PostgreSQL chunks 表
  -> index_service 过滤 child chunk
  -> embedding_service 生成向量
  -> vector_store upsert 到 Qdrant
  -> keyword_store 更新 PostgreSQL search_tsv
  -> 更新 ingest_task 状态

为什么 Phase 5 很关键

因为从这一阶段开始，系统第一次拥有了“真正可被检索系统召回的索引数据”。没有 Phase 5，Phase 4 的 chunk 仍然只是数据库里的结构化文本，后续 retrieval 根本没有底层索引可用。

为什么只索引 child chunk

因为后续检索阶段需要更细粒度的召回单元，child 更适合做向量检索和关键词检索；parent 则更适合在命中后回填更大上下文。所以当前不是“把所有 chunk 一起索引”，而是从现在开始就严格区分“谁用于召回、谁用于回填”。

5. 关键设计点为什么这样做

面试里最常见的追问，几乎都在“为什么”上。

1）为什么 embedding 与 reranker 都要本地加载？

因为规格明确要求第一版使用本地 Qwen Embedding 和本地 Qwen3 Reranker，而不是远程 API 或 OpenAI-compatible 代理。这样后续部署和数据边界更可控，也更符合私有知识库场景。

2）为什么当前只把 reranker 做成服务封装，而不接入查询链路？

因为 Phase 5 的职责是“把索引相关底座补齐”，而不是提前做 retrieval。当前先保证 reranker 模型能真实加载、真实调用，等到 Phase 6 再把它接进召回排序流程。

3）为什么 `index_service` 必须单独存在？

因为 worker 应该只负责驱动主流程，不应该自己散落地拼 embedding、Qdrant 和 FTS 细节。把这三步集中到 `index_service` 后，payload 结构更统一，也更容易测试调用顺序和边界规则。

4）为什么 Qdrant payload 里要带 `is_active`？

因为后续 delete / replace / 版本切换都会依赖一致的可见性控制。如果只有数据库里有 `is_active`，但向量侧没有，后续过滤就会出现状态不一致的问题。

5）为什么 `search_tsv` 现在就要更新？

因为 Phase 1 只有字段和索引结构，不代表关键词索引链路已经真的完成。Phase 5 必须把写入逻辑补齐，这样 Phase 6 才能直接在现成索引上做 FTS 查询。

6）为什么现在完成了索引，还不能说“查询能力完成”？

因为当前只完成了“可检索的数据准备”，还没有实现 query API、向量搜索接口、FTS 查询接口、RRF、metadata filter、query rewrite 和 answer generation。所以当前完成只能理解为“Phase 5 阶段目标完成”。

6. 面试官高频追问与答题思路

下面这些问题，就是你讲到当前阶段时大概率会被追问的点。

Q1：你们现在的 embedding 是怎么接的？
A：当前是独立的本地 embedding_service 封装，统一负责模型目录加载、单条 / 批量向量化和维度校验。worker 不直接接触底层模型细节，而是通过 index_service 间接调用。
Q2：为什么只索引 child chunk，不把 parent 也一起放进 Qdrant？
A：因为 child 是未来的细粒度召回单元，parent 是命中后回填更大上下文的辅助单元。如果 parent 也一起索引，会让召回粒度混乱，并破坏后续引用与上下文设计。
Q3：为什么还要单独维护 PostgreSQL FTS？
A：因为后续系统不是纯向量检索，而是向量 + 关键词混合检索。FTS 对法规编号、标准编号、英文术语、CVE 编号等精确文本信号很重要，所以 Phase 5 必须先把 `search_tsv` 更新链路打通。
Q4：reranker 现在已经在实际查询里用了吗？
A：还没有。当前只完成了本地 reranker 模型封装和基本调用能力，真正接到查询链路属于 Phase 6 的范围。
Q5：你们现在已经能回答用户问题了吗？
A：还不能准确这么说。当前只是把索引底座准备好了，查询接口、混合召回、排序和答案生成都还没有接起来，所以只能说“系统已经具备后续检索所需索引能力”。
Q6：worker 为什么要继续负责建索引？
A：因为 ingest 链路的语义本来就是“把上传文件变成可用知识单元”。Phase 4 把文本变成 chunk，Phase 5 就顺着同一条异步链路把 child chunk 变成真正可检索索引，这样流程边界最清晰，也最符合分阶段演进。

9. 你该怎么口述这个项目

最后给你一个适合面试场景的口述模板。

我做的是一个网络安全领域 RAG 知识库后端项目。这个项目是按 Phase 逐步推进的：先完成工程骨架和基础设施联通，再完成数据库地基、上传入口、解析清洗和结构化切分。当前推进到 Phase 5，核心是把数据库里的 child chunk 进一步变成真正可检索的索引数据。现在系统已经能对 child chunk 生成本地 embedding，写入 Qdrant，同时更新 PostgreSQL 的 `search_tsv` 字段，并统一维护后续检索要用的 metadata payload。这样虽然还没有进入 query/retrieve 和答案生成阶段，但已经把后续检索系统最关键的索引底层准备好了。
