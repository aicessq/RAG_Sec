1. 一句话定义当前项目状态

到了 Phase 8，项目第一次可以说自己“有问答能力”，但必须强调它是“证据约束问答”，不是自由发挥的聊天。

推荐表述：
这是一个面向网络安全知识资料的 RAG 后端项目，当前已经完成到 Phase 8。系统不仅已经能做 safety、intent、query rewrite 和混合检索，还能基于召回证据补回 parent context，生成带 citations 的答案，并在返回前做引用一致性检查；如果证据不足，则明确返回保守结论而不是编造。

2. Phase 8 相比 Phase 7 升级了什么

面试官通常会问：你们 Phase 7 已经能 rewrite 和 retrieve 了，那 Phase 8 的本质变化到底是什么？

Phase 6 已完成

系统能做向量检索、关键词检索和 RRF 融合，返回 top_k child chunks。

Phase 7 已完成

系统能在检索前做 safety、intent、term expansion、rewrite 和 filter builder。

Phase 8 当前

系统能把检索证据组织成答案，给出 citations，并做引用一致性检查与 query_log 留痕。

本质升级： Phase 7 让输入更安全、更可检索；Phase 8 则让系统第一次能把证据真正转化为“可返回给用户的答案”。

3. 当前到底实现了哪些内容

parent context 回取

系统会先用 child chunk 命中，再尝试基于 parent_chunk_id 回取 parent 文本，给生成层更多上下文。

answer_generator

backend/app/services/answer_generator.py 负责把 evidence contexts 组织成 answer 与 citations。

citation_checker

citation_checker.py 校验 citations 是否真实存在，以及页码、章节、条款号是否来自 metadata。

/query/answer

POST /api/v1/query/answer 串起 safety、rewrite、retrieve、parent context、answer、citation check、query_log。

query_log

当前会记录 user_query、rewritten_query、intent、filters、retrieved_chunk_ids、answer、status、latency、model_name。

证据不足保守回答

当没有足够证据或 citations 无法校验通过时，系统会返回“当前知识库未检索到明确依据”。

4. 问答链路怎么讲清楚

这是 Phase 8 面试里的主线，要能一口气讲顺。

user query
  -> safety_guard
  -> intent_classifier
  -> term_expander
  -> query_rewriter
  -> metadata_filter_builder
  -> hybrid retrieval (vector + keyword + RRF)
  -> parent context fetch
  -> answer_generator
  -> citation_checker
  -> query_log persistence
  -> answer + citations

4.1 当前 `/query/answer` 返回什么

字段 含义 为什么重要
answer 基于当前证据生成的答案 这是用户真正消费的核心结果
citations 引用的 chunk 与位置信息 证明答案不是空口生成
retrieved_chunks 检索命中的 child chunks 方便调试“证据是否合理”
debug.evidence_contexts 生成层看到的上下文 能验证 parent context 是否真正补了回来
evidence_status grounded / partial / insufficient / blocked 直接反映答案是否真的站得住

4.2 为什么 parent-child 设计在这里才真正体现价值

前几个阶段里，parent-child 更像“先设计好结构”；到了 Phase 8，它第一次真正参与业务：child 负责检索命中，parent 负责给生成层补回更完整的局部上下文。

5. 关键设计点为什么这样做

为什么 answer_generator 不能直接裸返回？
因为只生成答案而不校验引用，会把系统重新推回“像聊天模型一样会说，但不一定站得住”的状态。Phase 8 的目标是有证据约束的回答，不是流畅但无法验证的回答。
为什么 citation_checker 不是可选优化？
因为它是对 answer_generator 的兜底边界。至少要确保引用 chunk 存在、标题一致、页码一致、章节/条款号来自真实 metadata。否则系统很容易在最后一步出现“看起来像有依据，实际上引用错了”的问题。
为什么证据不足时要明确说不足，而不是尽量回答？
因为 RAG 项目的可信度来自“知道什么、也知道自己不知道什么”。在网络安全与法规场景里，证据不足时硬答往往比不答更危险。
为什么 query_log 要在这个阶段接进来？
因为到 Phase 8，一次 query 已经具备完整业务链路信息，可以真实记录检索证据、答案、状态和耗时，这些数据会直接支撑后续评测与优化。
为什么仍然没有做 reranker 主链路接入？
因为当前 Phase 8 的任务是把“基于证据回答”打通，而不是继续扩展更后续的优化阶段。严格按 phase 边界推进，能避免架构过早膨胀。

6. 面试官高频追问与答题思路

Q1：Phase 8 完成后，项目第一次多了什么真正“能给用户看”的能力？
第一次具备了面向用户的证据约束问答能力：不是只返回 chunks，而是返回 answer + citations，并能说明这些结论来自哪里。
Q2：为什么你们一定要回取 parent context？
因为 child chunk 为了检索通常较短，单独生成答案时可能上下文不完整；parent text 能补回结构上下文，让回答更稳，也更接近原文语义边界。
Q3：citation_checker 检查的最小集合是什么？
至少检查：引用 chunk 是否存在、doc_title 是否一致、page_start/page_end 是否一致、chapter/section/article_no 是否来自证据 metadata。
Q4：当前已经算完整 RAG 吗？
已经具备“可用问答闭环”的核心骨架，但还不是全部规划终点，因为 replace/chunk diff、评测体系和更完整优化链路还在后续 Phase。
Q5：如果用户提的是明显攻击问题，Phase 8 会怎么走？
仍然先经过 safety_guard。如果不是 allow，会直接返回安全结果并记录 query_log，不再继续进入检索和答案生成阶段。

面试官会问“你怎么证明这块真的打通了”，所以你要能说出测试点。

pytest backend/tests/test_citation_checker.py

建议的手动验证思路

  1. 给一个法规问题，确认返回 answer 与 citations
  2. 确认 citations 至少带 doc_title、page_start、page_end
  3. 观察 debug 字段中是否存在 parent_text
  4. 给一个证据不足的问题，确认系统返回保守答案
  5. 查看 query_logs 是否记录了链路关键字段

9. 你该怎么口述这个项目

适合面试里的完整说法：
我们这个项目是一个面向网络安全法规、标准、教材和知识资料的 RAG 后端系统。前几个阶段已经把上传、解析清洗、结构化切分、索引建立、混合检索和查询理解打通了。到 Phase 8，我们第一次把它升级成一个能真正回答用户问题的系统：先通过 safety、intent 和 query rewrite 整理输入，再做混合检索，命中 child chunk 后补回 parent context，接着生成带 citations 的答案，并在返回前用 citation checker 检查引用是否真实、页码是否一致。这样系统就不是“只会返回片段”，而是“能基于证据回答”。

建议你始终强调：Phase 8 的关键词不是“更会说”，而是“更会基于证据说”。
