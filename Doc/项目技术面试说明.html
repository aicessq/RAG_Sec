CyberSec RAG Agent · 项目技术面试说明

这是一份面向面试场景的项目说明文档，帮助你从“项目做了什么、为什么这么设计、技术怎么选、架构怎么讲”四个角度，把当前代码库讲清楚。

项目类型：网络安全领域 RAG 后端 当前进度：Phase 10 关键词：FastAPI / PostgreSQL / Qdrant / Redis / Celery / RAG / Eval

1. 这个项目一句话怎么说

这是一个面向网络安全法规、标准、教材和知识资料的 RAG 后端系统。它不仅能做文档上传、解析、切分、索引、检索和带引用回答，还支持文档增量更新、软删除以及基于 golden dataset 的量化评测。

2. 为什么这个项目不是“普通聊天机器人”

有明确知识边界

核心知识来自法规、标准、教材、手册等结构化资料，而不是开放互联网自由聊天。

有安全边界

查询链路最前面有 safety_guard，会拒绝攻击、绕过、入侵类请求。

有证据要求

回答不是裸生成，而是要经过 retrieval、parent context、citation check 才能返回。

有工程维护能力

支持 replace、chunk diff、向量复用、soft delete 和 eval，不是“一次性 demo”。

3. 这个项目的技术栈怎么讲最合理

FastAPI + Pydantic

负责 API、请求响应契约、Swagger 文档，适合快速构建分层清晰的后端。

SQLAlchemy + Alembic + PostgreSQL

负责文档、版本、chunk、任务、日志、评测结果等数据落库，并承担 PostgreSQL FTS。

Redis + Celery

负责 ingest / replace / reindex 这类异步任务，把重处理从同步接口中拆出去。

Qdrant

负责 child chunk 的向量检索，是 hybrid retrieval 的 semantic search 部分。

PyMuPDF

负责 PDF 解析，为后续清洗、chunk、引用页码提供基础文本来源。

sentence-transformers / torch

负责本地 embedding 与 reranker 推理，是检索质量的基础。

4. 架构主链路怎么说

上传链路：
upload
  -> 原始文件存储
  -> file_hash
  -> document / version / ingest_task
  -> Celery worker
  -> parse
  -> clean
  -> parent-child chunk
  -> embedding / index

查询链路：
query
  -> safety_guard
  -> intent / term expansion / rewrite
  -> metadata filter
  -> vector search + PostgreSQL FTS
  -> RRF fusion + rerank
  -> parent context
  -> answer_generator
  -> citation_checker

维护链路：
replace
  -> file_hash compare
  -> chunk_hash diff
  -> unchanged vector reuse
  -> visibility sync

eval 链路：
golden_dataset.jsonl
  -> eval_service
  -> Recall@K / MRR / citation accuracy / refusal accuracy
  -> eval_runs / eval_run_items

5. 面试官最容易追问的设计点

为什么要用 PostgreSQL + Qdrant，而不是只用一个存储？
因为这个项目做的是 hybrid retrieval。PostgreSQL 既承担主业务数据，也承担 FTS；Qdrant 专门做向量检索。两者职责分开更清晰，也更符合工程上的可维护性。
为什么 chunk 要分 parent 和 child？
child chunk 负责被检索命中，parent chunk 负责补上下文。这样既能保持检索粒度足够细，又不会丢掉回答时需要的上下文信息。
为什么 safety_guard 要放在 query 最前面？
因为这是网络安全领域系统，必须优先判断请求是否属于攻击、绕过、入侵类危险意图。安全边界不能放在回答之后，而要前置。
为什么 update 不是直接全量重建索引？
因为规格明确要求增量更新。项目通过 file_hash 和 chunk_hash diff 只处理真正变化的 child chunk，并复用 unchanged 向量能力，避免每次替换都全量重建。
为什么还要做 Phase 10 的评测体系？
因为一个 RAG 系统不能只说“感觉回答不错”。必须有可重复数据集和指标，才能判断检索、拒答、引用质量是否真的改善了。

6. 这个项目适合怎么讲成亮点

亮点 1：不是只做 API 壳

项目实现了从 ingest 到 answer，再到 update 和 eval 的完整后端闭环。

亮点 2：有明确的工程边界

API 层保持薄，主要逻辑都放在 services 层，利于维护和测试。

亮点 3：有安全属性

不是通用问答，而是把安全边界、拒答和合规回答放到设计核心。

亮点 4：有可持续演进能力

支持 replace、chunk diff、soft delete、eval run，说明项目考虑了长期维护而非一次性展示。

7. 如果面试官问“你做了哪些技术决策”

一个比较完整的回答方式是：

我把项目拆成了几层：FastAPI 负责 API，Pydantic 负责契约，SQLAlchemy + PostgreSQL 负责结构化数据和 FTS，Qdrant 负责向量检索，Redis + Celery 负责异步任务，service 层负责把解析、切分、检索、回答、更新和评测串起来。这样做的好处是系统边界清晰，既能支撑 RAG 主链路，又能支持后续的增量更新和效果评测。

8. 项目阶段演进怎么概括

Phase 0-1：工程骨架 + 数据库基础
Phase 2-4：上传、解析、清洗、chunk
Phase 5-6：索引、混合检索
Phase 7-8：安全、rewrite、证据约束回答
Phase 9：replace、增量更新、soft delete
Phase 10：eval dataset、指标化评测
最适合面试里的表达是：这个项目不是一开始就试图做“大而全”，而是按 phase 逐层补齐，从可运行、可检索、可回答，一直推进到可维护、可评测。

9. 最后一句总结

如果只能用一句话总结这个项目，你可以说：

这是一个面向网络安全知识资料的工程化 RAG 后端，不仅打通了上传、切分、检索和回答，还补齐了安全边界、增量更新、软删除和评测体系，因此它更像一个可持续演进的知识系统，而不是一次性问答 Demo。
