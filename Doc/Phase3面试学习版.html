1. 一句话定义当前项目状态

面试里最重要的能力之一，是能用一句话把当前系统成熟度讲准确，而不是泛泛地说“我做了个 RAG 项目”。

推荐表述：
这是一个面向网络安全知识资料的 RAG 后端项目，当前已经完成到 Phase 3。系统不仅能接收新文档并创建异步入库任务，还已经能把 PDF / Markdown / TXT 原始文件解析为统一的中间文本结构，保留页码，并做基础文本清洗；如果解析失败，还会把 ingest_task 明确回写为失败状态。但当前还没有进入 chunk 切分、向量化、索引、检索和答案生成阶段。

2. Phase 3 相比 Phase 2 升级了什么

面试官更关心“系统能力发生了什么升级”，而不是“你又写了哪些文件”。

Phase 1 已完成

解决数据库模型、迁移和持久化地基问题。

Phase 2 已完成

解决上传入口、原始文件落盘、任务入口和异步投递问题。

Phase 3 当前重点

解决“文件进入系统后，如何可靠地提取可处理文本并保住页码”的问题。

本质升级

  • 系统从“只会接收文件”升级为“已经开始理解原始文件内容”。
  • worker 不再只是占位修改状态，而是开始真正执行解析与基础清洗。
  • 后续 Phase 4 的 chunk 切分，现在已经有统一输入结构可消费。

4. 解析链路怎么讲清楚

真正体现理解深度的，不是“我做了 parser”，而是能把输入到输出说成一个完整闭环。

推荐你背下来的处理顺序

客户端上传文件
  -> FastAPI route 接收 multipart/form-data
  -> upload_service 保存原始文件并创建 document/version/task
  -> Celery worker 收到 ingest_document_task
  -> 将 ingest_task.status 更新为 processing
  -> parser_service 按后缀解析 PDF / Markdown / TXT
  -> 统一输出 ParsedDocument / ParsedPage
  -> cleaner_service 做基础保守清洗
  -> 成功时写阶段性完成说明
  -> 失败时写 failed + error_message

为什么这条链路很关键

因为 Phase 3 解决的是“原始文件如何变成后续可处理文本”这个问题。没有这个阶段，后面的 chunk、embedding 和检索都无从谈起。

页码保留意味着什么

它不代表当前已经有 chunk metadata 落库，而是说明：后续 Phase 4 在切分 chunk 时，已经有可继承的 page_number 基础信息。这一步是为将来的 page_start/page_end 做准备。

5. 关键设计点为什么这样做

面试里最容易被追问的，往往都是“为什么”。

1）为什么 parser 和 cleaner 必须拆开？

因为 parser 负责“尽量忠实提取”，cleaner 负责“最低必要整理”。如果混在一起，后续很难判断问题究竟是提取阶段丢了文本，还是清洗阶段把文本处理坏了。

2）为什么需要统一 ParsedDocument / ParsedPage？

因为后续 chunk_service 不应该关心源文件到底是 PDF、Markdown 还是 TXT。统一中间结构能让后续阶段只处理一种输入模型，减少分支复杂度。

3）为什么 Markdown / TXT 直接视作单页？

因为它们没有天然页码。Phase 3 的目标是保证接口一致，而不是发明复杂伪分页策略。单页策略简单、稳定、可解释，也足够支撑后续阶段继续推进。

4）为什么 cleaner 要非常保守？

因为像法规条款号、标准编号、CVE 编号、代码块、表格结构这些内容，一旦被“清洗坏”，后续切 chunk 和检索都很难补救。所以当前策略是宁可少清一些，也不要误伤关键信息。

5）为什么失败时一定要回写 ingest_task？

因为只打日志对调用方是不可见的。任务失败必须体现在数据库状态上，系统外层才能知道“上传成功了，但后台解析失败了”，这也是异步系统最基本的可观测性要求。

6）为什么当前 worker 成功不等于“知识入库完成”？

因为解析与清洗只是 ingest pipeline 的前半段。后面还有 chunk、embedding、向量入库、关键词索引等步骤，所以当前成功只能理解为“Phase 3 阶段目标完成”，不能夸大成“文档已经可检索”。

6. 面试官高频追问与答题思路

下面这些问题，基本就是你讲到当前阶段时最容易被问到的点。

Q1：你们现在已经能解析哪些文件？
A：当前支持 PDF、Markdown 和 TXT。PDF 按页解析并保留真实页码，Markdown/TXT 当前统一视作单页文档处理。
Q2：为什么不在 parser 里直接顺手把 chunk 也切了？
A：因为这会直接越过 Phase 边界。Phase 3 的职责是“提取 + 清洗”，Phase 4 才是结构化切分。现在强行加 chunk，会把 parser、cleaner 和 chunk 逻辑耦合在一起，不利于后续维护和验收。
Q3：清洗阶段最容易出什么问题？
A：最容易误伤条款编号、标准编号、CVE 编号、代码块和表格结构。所以当前 cleaner 是保守策略，只处理明确噪声，不做结构化语义改写。
Q4：为什么要统一 ParsedDocument，而不是让不同 parser 返回不同结构？
A：因为后续 chunk_service 和检索链路不应该知道上游原始文件类型。统一结构可以把文件类型差异限制在 parser 层，减少整个系统的耦合面。
Q5：如果 PDF 损坏了怎么办？
A：当前实现会抛出解析错误，worker 会捕获异常，把 ingest_task.status 写成 failed，并把错误信息写到 error_message，避免静默失败。
Q6：那你们现在能检索这些解析后的文档了吗？
A：还不能。当前阶段只负责把原始文件变成统一可处理文本，并保留页码与失败状态。真正检索要等 chunk、索引和检索链路补齐之后才成立。

手动验证思路

  -> 确认 ingest_task 进入 processing

  -> 损坏 PDF 时确认 status=failed 且 error_message 有内容

注意：当前“成功”只代表 Phase 3 的解析/清洗阶段成功，不代表文档已经完成完整知识入库。

9. 你该怎么口述这个项目

最后给你一个适合面试场景的口述模板。

我做的是一个网络安全领域 RAG 知识库后端项目。这个项目是按 Phase 逐步推进的：先完成工程骨架和基础设施联通，再完成数据库模型和迁移，然后完成上传入口。当前推进到 Phase 3，重点是把“原始文件如何变成后续可处理文本”这件事落地。现在系统已经能把上传后的 PDF、Markdown、TXT 解析成统一的中间结构，保留页码，并通过独立 cleaner 做基础清洗；如果解析失败，还会把异步任务状态明确写回数据库。这样虽然还没有进入 chunk、索引和问答，但已经把后续 ingest pipeline 所需的文本输入层搭出来了。
