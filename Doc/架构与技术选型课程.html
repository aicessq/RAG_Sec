架构与技术选型课程

本课程把「这个项目怎么搭」和「为什么选这些技术」合在一起讲。 目标不是背名词，而是能从业务边界、分层职责、数据流和工程约束出发， 把 CyberSec RAG Agent 讲成一个可维护、可评测、可演进的系统。

课程类型：架构 + 技术选型 当前实现：Phase 10 关键词：分层 / Hybrid RAG / Async / Eval 来源：当前仓库真实实现

目录

1. 先建立全局图景

先回答“这是什么系统”，再谈技术栈才有意义。

一句话定位： 这是一个面向网络安全法规、标准、教材与知识资料的 RAG 后端系统。 它能上传与版本化文档、解析切分并建立索引、混合检索后给出带引用的回答， 还支持增量更新、软删除，以及基于 golden dataset 的量化评测。

它不是什么

  • 不是开放域自由聊天机器人
  • 不是“只写 prompt 的 demo”
  • 不是把所有文本丢进向量库就结束
  • 不是同步阻塞式单进程脚本

它必须具备什么

  • 明确知识边界：只答库内资料能支撑的内容
  • 安全边界：查询前先做 safety_guard
  • 证据约束：回答要能对上 citation
  • 工程维护：replace / soft delete / eval

为什么这个定位会决定架构

安全领域资料往往是 PDF/标准文本，条款编号、页码、版本都很重要。 因此系统必须同时管理：

  1. 文档生命周期：上传、版本、替换、软删除
  2. 检索资产：child chunk 向量 + FTS + parent context
  3. 查询治理：安全过滤、意图、改写、引用校验
  4. 效果度量：Recall@K / MRR / citation accuracy 等

这四件事决定了：不能只选一个 LLM API，而要选一套“API + 关系库 + 向量库 + 异步任务 + 评测”的组合。

2. 仓库与运行时分层

先看目录，再看请求如何穿过这些目录。

2.1 仓库形状

路径 职责
backend/app/ 后端应用核心：API、services、models、workers、prompts
backend/alembic/ 数据库 schema 迁移
backend/tests/ 默认单测 + integration 基础设施测试
frontend/ React + TypeScript + Vite 的 MVP 前端
eval/ golden dataset 与评测数据源
Doc/ 规格、架构、学习型 HTML 与阶段文档
docker-compose.yml PostgreSQL / Redis / Qdrant / backend / worker 编排

2.2 运行时五层

HTTP 请求 → main.py（应用入口 / CORS / 日志 / 路由挂载） → api/*（薄路由：参数、状态码、异常映射） → services/*（真正业务：解析、检索、回答、更新、评测） → models + db + Alembic（持久化与 schema） → workers/* + Celery（异步 ingest / replace） → PostgreSQL / Redis / Qdrant / 本地模型
核心工程原则： API 层只接请求，真正的流水线逻辑沉到 services / workers。 这样路由保持薄，业务可测，worker 也能复用同一套 service 能力。

2.3 各层该做什么 / 不该做什么

该做

  • api/：路径定义、依赖注入、HTTP 错误映射
  • services/：pipeline 编排与领域规则
  • models/：关系建模、约束、默认值
  • workers/：长任务编排，调用 services

不该做

  • 在路由里写完整 ingest / retrieve 流水线
  • 让 worker 绕过 service 直接散落业务细节
  • 把 parent/child 规则散写到多个入口
  • 让前端假设后端没有版本与可见性语义

3. 四大业务主链路

架构不是静态模块列表，而是四条真实会跑起来的数据流。

3.1 Upload / Ingest

upload → 校验扩展名 / MIME / 大小 → 计算 file_hash，落盘原始文件 → 创建 document / document_version / ingest_task → Celery enqueue → parse → clean → parent/child chunk → chunks 写入 PostgreSQL → 仅 child chunk 进入 embedding / Qdrant / FTS → 任务完成

同步接口只做“接住文件 + 建记录 + 派任务”； 解析、切分、embedding 这些重活在 worker 中完成，避免 HTTP 超时。

3.2 Query / Answer

user query → safety_guard → intent_classifier → term_expander → query_rewriter → metadata_filter → vector search (Qdrant) + keyword search (PostgreSQL FTS) → RRF fusion → rerank → parent-context 回填 → answer_generator → citation_checker → 返回回答 + 写 query_log
查询链路把 安全过滤放在最前面，把 证据校验放在生成之后。 这是领域约束，不是可选装饰。

3.3 Replace / Soft Delete

Replace（增量更新）

  1. 上传新文件并与当前 file_hash 比较
  2. 创建新 document_version + ingest_task
  3. 重新 parse / clean / chunk
  4. 按 chunk_hash diff child chunks
  5. 新增的做 embedding；未变的复用向量
  6. 移除的在 PG / Qdrant / FTS 中失活
  7. 切换 current_version_id

Soft Delete

  • 不是直接物理删主表完事
  • 同步关闭 document / chunk 可见性
  • 同步关闭 Qdrant payload is_active
  • 同步关闭 FTS 可见性

目标：默认检索范围再也看不到已删除内容， 且三处索引状态保持一致。

3.4 Eval

eval/golden_dataset.jsonl → materialize eval_datasets / eval_dataset_items → 对每条样本跑真实 safety / rewrite / retrieve / answer → 计算 Recall@K / MRR / citation accuracy / refusal accuracy / latency → 落库 eval_runs / eval_run_items

评测复用真实查询流水线，而不是另写一套 mock 路径。 这样评测结果更能反映线上行为。

4. 数据与索引架构

PostgreSQL 是真相源；Qdrant 是语义检索加速层；Redis 是任务协作层。

4.1 核心实体

文档生命周期

documents

document_versions

ingest_tasks

检索资产

chunks（parent / child）

search_tsv

Qdrant child vectors

观测与评测

query_logs / feedback

eval_datasets / items

eval_runs / items

4.2 Parent / Child 设计

类型 存哪里 干什么 不干什么
Child chunk PostgreSQL + Qdrant + FTS 精确命中、向量检索、关键词检索、diff 单元 不直接作为完整回答上下文
Parent chunk 主要在 PostgreSQL 命中后回填更完整上下文 默认不进入向量 / 关键词检索面
为什么这样拆： child 更适合检索粒度，parent 更适合生成时的上下文完整性。 同时 chunk_hash 让 replace 可以做增量 diff，而不是整库重嵌。

4.3 三处可见性必须对齐

软删除和版本切换时，下列三者要同时正确：

  1. PostgreSQL 中 document / chunk 的 active 状态
  2. PostgreSQL FTS 可检索范围
  3. Qdrant payload / 过滤条件中的 active 状态

任何一处漏掉，都会出现“库里说删了，检索还能搜到”的一致性 bug。

5. 技术栈全景

按职责分组，而不是按流行度罗列。

API

Python 3.11+ / FastAPI / Pydantic v2

后端语言、HTTP 入口、请求响应契约、配置建模、Swagger 文档。

Data

SQLAlchemy 2.x / Alembic / PostgreSQL

关系建模、schema 迁移、业务真相源，并承担 FTS 关键词检索。

Async

Redis / Celery

任务队列、结果后端、ingest / replace / reindex 异步执行。

Vector

Qdrant

child chunk 向量存储与语义检索，支持 metadata payload 过滤。

AI

PyMuPDF / sentence-transformers / torch / LLM

PDF 解析、本地 embedding / reranker、回答生成与引用检查。

Ops / QA

Docker Compose / pytest / TestClient / httpx

多服务编排、分层测试、接口契约与真实基础设施验证。

前端补充

frontend/ 使用 React + TypeScript + Vite 驱动现有 FastAPI 接口， 形成可演示的上传、查询、文档管理与评测入口。前端不是本项目最重的架构重心， 但说明系统已经具备“可被 UI 消费的稳定 API 面”。

6. 为什么这样选：逐项选型逻辑

每一项都对应一个真实约束，而不是“因为大家都在用”。

6.1 Python 3.11+

为什么选
  • FastAPI / Pydantic / SQLAlchemy / Celery / AI 生态成熟
  • 适合快速把 RAG 流水线工程化
  • 类型注解与现代语法对中大型后端可读性更好
如果换别的
  • Node 也行做 API，但本地 embedding / 文档 NLP 生态更偏 Python
  • Go/Java 更强并发与强类型，但 AI 原型与模型库摩擦更大

6.2 FastAPI + Pydantic v2

  • 开发效率：路由、校验、OpenAPI 文档一次成型
  • 契约清晰：upload / query / answer / eval 的输入输出靠 schema 约束
  • 分层友好：天然鼓励“薄 API + 厚 service”
  • 适合演进：分 phase 加接口时，文档和校验同步跟上
FastAPI 在这里是API 外壳，不是业务大脑。 面试时要强调：核心价值在 services 流水线，而不是框架本身。

6.3 PostgreSQL + SQLAlchemy + Alembic

PostgreSQL 承担双职责

  1. 业务真相源：文档、版本、chunk、任务、日志、评测
  2. Hybrid retrieval 的 keyword 底座：FTS

UUID、JSONB、GIN 索引都很适合“结构化元数据 + 半结构化内容”的 RAG 资产。

为什么不是“只用向量库”

  • 版本切换、软删除、任务状态需要事务与约束
  • 条款号、页码、active 标记需要关系建模
  • 评测 run 需要可查询、可对比的历史记录
  • FTS 能补语义检索在专有名词 / 编号上的短板

SQLAlchemy 负责复杂对象关系；Alembic 负责多阶段 schema 演进。 对一个持续加表（query_logs、eval_runs…）的项目，迁移工具不是可选项。

6.4 Redis + Celery

Ingest / replace 链路天然重：

  • PDF 解析耗时
  • chunk 与 embedding 计算重
  • 索引写入不是瞬时操作

所以上传接口只创建任务，worker 异步执行。 Redis 作为 broker / result backend，Celery 负责独立进程消费。 这是“同步 API 稳定性”和“重处理吞吐”之间的标准拆分。

6.5 Qdrant

选它的原因

  • 向量检索职责清晰，部署相对轻量
  • payload 适合带 metadata filter
  • 很适合中小型 RAG 快速落地
  • 与 PostgreSQL 分工明确：语义检索 vs 业务真相

刻意不做的事

  • 不把 parent chunk 全塞进向量库
  • 不把业务主数据只放在 Qdrant
  • 不让向量库单独决定“文档是否存在”

6.6 PyMuPDF

法规、标准、教材大量是 PDF。没有可靠逐页解析，就没有稳定页码引用， 也没有可清洗、可切分的文本来源。PyMuPDF 在速度与工程可用性上足够支撑 ingest。

6.7 sentence-transformers + torch + 本地模型

  • 可控：embedding / reranker 可本地运行，便于开发和离线验证
  • 可替换：封装在 service 层，模型实现可换而不改 API
  • 服务检索质量：torch 在这里主要用于推理，不是训练平台
仓库里的 fallback / 占位权重可以验证编排是否正确， 但不等于真实模型质量已经达标。讲选型时要区分“链路可用”和“效果已验证”。

6.8 Docker Compose + pytest

Docker Compose

本系统依赖 PostgreSQL、Redis、Qdrant、backend、worker 多组件协作。 Compose 解决的是“把整套依赖稳定拉起来”，而不是单纯容器炫技。

pytest 分层

默认快速测试不依赖真实基础设施； integration 标记专门打真实 PG / Redis / Qdrant。 这让日常开发和严格门禁可以分开。

7. 关键架构决策（比技术名词更重要）

面试官往往更关心“你做了哪些取舍”。

1. 薄 API，厚 Service

路由只做协议适配；流水线、diff、fusion、citation 都在 service。 好处：可测、可复用、worker 与 API 共享逻辑。

2. Upload ≠ Replace

上传创建新 document；替换创建新 version。 文档身份与版本历史被严格分开，避免“覆盖上传”语义混乱。

3. 只索引 Child Chunk

向量和 FTS 面向 child；parent 用于上下文重建。 检索粒度更细，生成上下文更完整，增量 diff 也更自然。

4. Hybrid Retrieval

向量负责语义相近；FTS 负责编号、专名、字面匹配。 再经 RRF / rerank 融合，比单路检索更稳。

5. Safety 在生成之前

安全过滤是 query 第一阶段，不是回答后处理。 对网络安全知识库，这是产品边界，不是附加功能。

6. 增量更新优于全量重嵌

用 file_hash 与 chunk_hash 识别变化， 未变 child 复用向量，降低 replace 成本与抖动。

7. 三存储可见性对齐

PostgreSQL / FTS / Qdrant 的 active 状态必须一致。 软删除和版本切换都围绕这个不变式设计。

8. Eval 走真链路

评测调用真实 safety / retrieve / answer， 指标可落库比较，避免“离线脚本很美、线上行为另一套”。

8. 技术如何协作：一张总图

用户 / 前端 (React + TS + Vite) │ ▼ FastAPI + Pydantic ← HTTP API 与契约 │ ├─ 同步查询 / 管理接口 ──► services/* │ ├─ safety / rewrite / retrieve / answer │ ├─ update / soft delete / eval │ └─ embedding / rerank / LLM │ └─ 上传 / 替换接口 ──► 创建 DB 记录 └─ Celery task (Redis) └─ worker ├─ PyMuPDF parse ├─ clean / chunk ├─ PostgreSQL 写 chunks / FTS └─ Qdrant 写 child vectors 持久化分工： PostgreSQL = 真相源 + FTS Qdrant = 语义检索 Redis = 任务协作 本地模型 = embedding / rerank /（可选）生成

用一句话串起来

用 FastAPI 暴露能力，用 PostgreSQL 管业务与关键词检索，用 Qdrant 做语义检索， 用 Redis + Celery 消化重处理，用本地 embedding/reranker 提升检索质量， 再用 pytest 与 Docker Compose 保证系统可验证、可运行。

9. 面试怎么讲（可直接口述）

Q1：请用 30 秒介绍这个项目的架构。
这是一个安全领域的 RAG 后端。入口是 FastAPI，业务在 services 层。 文档经 Celery 异步解析切分后，child chunk 进入 PostgreSQL FTS 和 Qdrant； 查询先过 safety，再做改写与混合检索，回填 parent context 后生成带引用回答。 另外支持基于 chunk diff 的增量替换、软删除，以及走真实链路的评测。
Q2：为什么同时用 PostgreSQL 和 Qdrant？
职责不同。PostgreSQL 是文档、版本、任务、日志、评测的真相源，并提供 FTS； Qdrant 专门做 child chunk 的向量检索。这样关系约束、事务和语义召回不会混在一个存储里。
Q3：为什么引入 Celery，而不是上传接口里直接处理完？
解析、切分、embedding、写索引都是长耗时操作。同步做会拉高延迟、放大超时风险。 上传接口只负责校验、落盘、建记录和入队；worker 异步执行，系统更稳。
Q4：为什么是 hybrid retrieval，而不是纯向量？
安全资料里有大量法规编号、条款号、专有名词。纯语义容易漏字面关键命中； 纯关键词又缺语义泛化。所以用 Qdrant + PostgreSQL FTS，再 RRF/rerank 融合。
Q5：你认为最关键的架构约束是什么？
有三条：第一，API 薄、业务在 service；第二，只索引 child、parent 做上下文； 第三，PostgreSQL / FTS / Qdrant 的可见性必须一致。这三条决定了系统能不能长期维护。
Q6：技术选型时你如何避免“为了 AI 而 AI”？
先固定业务不变式：要版本、要引用、要安全拒绝、要可评测。 然后再选能支撑这些不变式的组件。模型只是流水线中的一环， 存储一致性、异步边界和评测闭环同样关键。

10. 学完自测

不看文档，能否独立回答下面问题。

  1. 画出从 upload 到 child chunk 入 Qdrant 的完整路径，标出同步与异步边界。
  2. 说明 documents 与 document_versions 为什么要拆开。
  3. 解释为什么 parent chunk 默认不进入向量检索。
  4. 软删除时，如果只改 PostgreSQL 不改 Qdrant，会出现什么现象？
  5. 用自己的话说明：FastAPI、PostgreSQL、Qdrant、Celery 各自不可替代的理由。
  6. 评测为什么必须复用真实 query pipeline？
建议掌握标准： 你能不看代码，把分层、四条主链路、存储分工和 6～8 条选型理由讲顺， 就算真正理解了本项目的架构与技术选型。
