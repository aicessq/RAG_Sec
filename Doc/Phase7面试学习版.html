1. 一句话定义当前项目状态

面试里一个很常见的失分点，是把“能检索”误说成“能回答”。Phase 7 仍然要讲清楚边界。

推荐表述：
这是一个面向网络安全知识资料的 RAG 后端项目，当前已经完成到 Phase 7。系统不仅已经具备 child chunk 的混合检索能力，还能在检索前先做安全判断、意图分类、术语扩展、query 改写和 metadata filter 补全；但当前仍未进入最终答案生成和引用校验阶段。

2. Phase 7 相比 Phase 6 升级了什么

面试官更关心“输入进入检索前，系统多了什么能力”，而不是“你多写了一个接口”。

Phase 5 已完成

解决 child chunk 建索引：embedding、Qdrant、FTS 与统一 payload。

Phase 6 已完成

解决 query 检索：vector search、keyword search、RRF 与 `/query/retrieve`。

Phase 7 当前

解决 query 理解：safety_guard、intent、term expansion、rewrite、filter builder 与 `/query/rewrite`。

本质升级： Phase 6 让系统“能找”，Phase 7 让系统“在找之前，先把用户输入整理得更安全、更可检索、更可解释”。

3. 当前到底实现了哪些内容

安全边界

backend/app/services/safety_guard.py 使用规则优先方式输出 allow / refuse / redirect，用于在查询链路最前面拦截高风险请求。

意图分类

intent_classifier.py 将 query 归入 standard_query、law_query、textbook_query、vulnerability_fix 等类别。

术语扩展

term_expander.py 负责将“等保”“WAF”“EDR”“SQLi”等缩写或术语扩展成更利于检索的候选词。

查询改写

query_rewriter.py 生成 rewritten_query、search_keywords、sub_queries，但不直接生成答案。

过滤补全

MetadataFilterBuilder 坚持“显式 filter 优先，intent 推断只补充不覆盖”，避免系统把用户的明确约束改坏。

调试 API

POST /api/v1/query/rewrite 输出 safety、intent、expanded_terms、rewritten 与 filters，方便独立调试输入优化链路。

4. 输入优化链路怎么讲清楚

这一节是面试里的主线：从用户问题进入系统，到真正检索前都发生了什么。

user query
  -> safety_guard
  -> intent_classifier
  -> term_expander
  -> query_rewriter
  -> metadata_filter_builder
  -> (下一阶段才会继续进入完整 answer 主链路)

4.1 `/query/rewrite` 当前返回什么

字段 含义 为什么重要
safety 允许、拒绝或防御性重定向 证明系统在网络安全领域不是“无门槛回答器”
intent 问题属于法规、标准、教材、修复等哪类 决定后续的检索表达与文档类型倾向
expanded_terms 术语补全列表 兼顾缩写、全称、同义词与中英文表达
rewritten 改写 query、关键词、子查询 让向量检索和关键词检索都更容易命中
filters 最终结构化过滤条件 方便验证显式条件是否被保留、推断条件是否合理补充

4.2 当前为什么还不把 rewrite 直接接到最终回答里

因为当前更重要的是把输入优化链路做成一个可单独观察、可单独测试、可单独解释的阶段。只有当 rewrite 质量足够稳定，后续接入 answer generation 才不会把问题掩盖掉。

5. 关键设计点为什么这样做

为什么 safety_guard 必须放在最前面？
因为这是网络安全场景。若先检索、再判断，系统可能已经帮用户组织好了危险上下文。先判定 allow / refuse / redirect，才能真正形成防护边界。
为什么当前优先用规则而不是完全依赖 LLM？
因为规则更稳定、可解释、可测试，特别适合 Phase 7 这种要先建立边界和调试能力的阶段。LLMService 现在只是未来增强的预留包装层。
为什么 intent_classifier 还要输出 suggested_doc_types？
因为 query 的“问题类型”会影响默认检索倾向。比如标准类问题更适合优先看 standard / policy，但这只是补充建议，不能覆盖用户显式给定的过滤条件。
为什么 metadata_filter_builder 要强调“显式优先”？
因为用户自己传进来的过滤条件是明确意图，而 intent 推断只是系统猜测。若让猜测覆盖显式条件，系统就可能在检索范围上犯错。
为什么 query_rewriter 输出 search_keywords 和 sub_queries，而不只给一个 rewritten_query？
因为混合检索里，不同表示形式对不同召回通道有价值：一个统一 rewrite 适合整体表达，关键词适合 FTS，子查询适合后续多路并行召回与调试。

6. 面试官高频追问与答题思路

Q1：Phase 7 完成后，系统和 Phase 6 最大区别是什么？
Phase 6 解决的是“怎么检索”，Phase 7 解决的是“检索前怎么先把用户输入处理得更安全、更有结构、更适合召回”。
Q2：为什么你们要单独做一个 `/query/rewrite` 调试接口？
因为输入理解链路的问题不能和最终回答混在一起看。单独暴露 rewrite 调试接口，可以直接检查 safety、intent、扩展词、改写结果和 filters 是否符合预期。
Q3：如果用户问的是明显攻击问题怎么办？
当前由 safety_guard 在链路最前面识别，输出 refuse 或 redirect，并给出安全替代表达，例如转向检测、修复、日志排查或事件响应建议。
Q4：你们现在已经在 Phase 7 用上 LLM 了吗？
主链路还没有。当前主要是规则优先实现，以保证行为稳定和边界清晰。llm_service.py 已经预留好后续接入外部 LLM 的包装方式，但并未越界把它塞进 Phase 7 主流程。
Q5：为什么 Phase 7 还不能算完整问答？
因为问答至少还缺 answer generation、reranker 主链路接入、citation checker，以及最终答案与证据组织逻辑。Phase 7 只是在为这些后续能力整理一个更安全、更可控的输入入口。

7. 你需要会的运行与验证命令

面试官有时会追问你“那你怎么验证这块是对的”，下面这些命令和验证点要能说出来。

# 在项目专用虚拟环境 / conda 环境中运行
pytest backend/tests/test_safety_guard.py
pytest backend/tests/test_intent_classifier.py
pytest backend/tests/test_query_rewriter.py
pytest backend/tests/test_query_rewrite_api.py -m integration

建议的手动验证思路

  1. 给一个标准类问题，观察 intent 是否识别为 standard_query
  2. 给一个安全缩写问题，观察 expanded_terms 是否补出全称
  3. 给一个显式 doc_type 的请求，观察 filter builder 是否保留显式条件
  4. 给一个攻击性请求，观察 safety 是否输出 refuse 或 redirect

8. 现在明确还没做什么

完整 answer generation 未做

citation checker 未做

还没有对答案与证据片段做最终引用校验。

replace / chunk diff 未做

9. 你该怎么口述这个项目

适合面试里的完整说法：
我们这个项目是一个面向网络安全法规、标准、教材和知识资料的 RAG 后端系统。前面几个 Phase 已经完成上传、解析清洗、结构化切分、child chunk 建索引以及基础混合检索。到 Phase 7，我们进一步把查询入口前置成一个安全且可解释的输入优化链路：先做 safety_guard，判断请求是否应该允许、拒绝或重定向；再做意图分类、术语扩展、query 改写和 metadata filter 补全。这样后续进入答案生成时，输入就已经更安全、结构更清晰、召回目标也更明确了。

建议你在讲述时始终强调：Phase 7 已经具备“安全边界 + 查询理解”，但还不是最终问答闭环。
