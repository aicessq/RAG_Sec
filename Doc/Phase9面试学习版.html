CyberSec RAG Agent · Phase 9 学习文档

从“面试官会怎么追问你”这个角度，理解当前项目在 Phase 9 为什么开始真正具备长期维护能力，以及为什么 `chunk_hash diff`、unchanged child 复用与 soft delete 是这个阶段的关键词。

当前阶段：Phase 9 重点：replace / file_hash / chunk_hash diff / vector reuse / soft delete 下一阶段：Phase 10 eval

1. 一句话定义当前项目状态

这是一个面向网络安全知识资料的 RAG 后端项目。到 Phase 9，它已经不只是“能上传、索引、检索和回答”，还开始支持文档替换、增量更新、unchanged child chunk 向量复用、软删除与索引可见性同步关闭。

2. Phase 9 相比 Phase 8 本质升级了什么

Phase 8

重点是“基于证据回答”：query/answer、parent context、answer_generator、citation_checker、query_log。

Phase 9

重点是“长期维护能力”：已有 document 可以 replace，更新必须基于 chunk diff，删除必须让默认检索彻底看不见。

面试里要强调：Phase 8 解决的是能回答，Phase 9 解决的是能持续维护而不无谓重建。

3. 当前到底实现了哪些内容

replace 接口

POST /api/v1/documents/{document_id}/replace 为已有 document 创建新 version，而不是复用 upload 语义。

file_hash 快速比对

新文件和 current version 的 file_hash 一致时，直接返回 file_unchanged，避免无意义更新。

chunk_hash diff

child chunk 通过 chunk_hash 分为 added / removed / unchanged，diff 主键不是 chunk_index。

unchanged child 向量复用

旧 child 的向量可被复制到新 version 的对应 child 记录，避免重新 embedding。

soft delete

DELETE /api/v1/documents/{document_id} 会把 document 标为 deleted，并关闭 chunk 与索引可见性。

Qdrant / FTS 可见性同步

删除或 removed chunk 会同步关闭 Qdrant payload 的 is_active，并清空 FTS 可见性。

4. Phase 9 主链路怎么讲清楚

replace request
  -> check document exists
  -> read upload bytes
  -> compare file_hash with current version
  -> if unchanged: return file_unchanged
  -> else create new version + replace ingest_task
  -> later perform chunk_hash diff on child chunks
  -> added: embed + upsert + FTS
  -> unchanged: copy old vector, don't re-embed
  -> removed: is_active=false + payload invisible + FTS invisible

5. 面试官最爱追问的设计点

为什么 diff 主键一定是 chunk_hash，而不是 chunk_index？
因为 chunk_index 很容易因为切分位置变化而整体偏移，导致大量误判。chunk_hash 才能表达“这段 child 文本语义是否真的没变”。
为什么 unchanged child 还要在新 version 下保留数据库记录？
因为数据库层面需要表达“新版本也包含这些 chunk”；但索引层面又不能重新 embedding，所以要做的是“新记录 + 旧向量复用”。
为什么 soft delete 不能只改 documents.status？
因为如果只改主表状态但不关闭 chunk / Qdrant / FTS，可检索结果里仍可能看到已删除文档，这会造成严重的可见性错误。
为什么 replace 不能混进 upload？
因为 upload 的语义是“创建新 document”，replace 的语义是“在已有 document 上创建新 version”。这两个动作的约束完全不同。

7. 现在明确还没做什么

自动同步法规

当前没有实现自动从外部来源拉取或刷新法规内容。

复杂版本对比报告

当前只实现更新链路本身，没有实现可视化版本对比页面。

完整评测体系

后续 Phase 10 才进入 eval dataset / eval run 的真正业务化使用。

默认全库重建

这正是 Phase 9 明确避免的路径，更新必须尽量增量化。

8. 你该怎么口述这个项目

一个很适合面试里的说法是：前面几个阶段把 RAG 的入库、索引、检索和回答打通了；而 Phase 9 开始解决真正工程化的问题——当法规、标准或教材更新时，系统如何只更新有变化的 child chunk，复用 unchanged chunk 的向量能力，并在删除时同步关闭数据库和索引可见性，而不是粗暴全量重建。
