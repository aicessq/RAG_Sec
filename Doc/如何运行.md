## 3. 当前已知约束

1. 必须使用项目专用 conda 环境
   - 不要使用全局 Python 直接运行项目
2. 本地启动 FastAPI 时，必须从 `backend/` 目录启动
   - 应用入口为 `backend/app/main.py`
3. 数据库迁移使用 Alembic
   - 配置文件在 `backend/alembic.ini`
4. 当前最稳妥的迁移执行方式是：
   - **从项目根目录执行**
   - 使用 `alembic -c backend\alembic.ini upgrade head`
5. 本地开发建议：
   - Docker 只拉起 `postgres` / `redis` / `qdrant`
   - 后端使用本地 conda 环境运行
   - 前端使用本地 npm 运行
   - Celery worker 也优先使用本地 conda 环境运行
6. Windows 下如果杀毒软件误报：
   - 建议把 `D:\Code_MyProject\RAG_Sec\backend\app\services\` 加入白名单
   - 避免误删 `safety_guard.py`
7. 当前 FastAPI 0.139.0 环境里，`app.routes` 里会出现 `_IncludedRouter`
   - 不应再仅靠 `app.routes` 是否全是 `APIRoute` 来判断接口有没有挂载
   - 应结合 `/openapi.json`、`/docs` 或真实请求验证
8. 前端开发服务器使用 Vite，已配置代理到后端：
   - 前端地址：`http://localhost:5173`
   - 请求 `/api` 路径会自动转发到 `http://localhost:8000/api`
9. 当前推荐开发方式不是“每改一次都重建整套 Docker”，而是：
   - Docker 负责跑 `postgres` / `redis` / `qdrant`
   - 本地用 `uvicorn --reload` 跑 FastAPI
   - 本地用 `celery worker` 跑异步任务
   - 逻辑调通后，再统一 `docker compose up -d --build` 做容器集成验证
10. 原因是：
   - Python / Celery 代码改动频繁时，本地热重载反馈更快
   - Celery 任务注册、服务层逻辑、接口联调问题通常先在本地更容易定位
   - Docker 更适合做“最终环境一致性验证”，而不是每次改动都承担构建成本

## 4. 启动总流程

按以下顺序执行：

1. 准备 conda 环境
2. 安装后端依赖
3. 启动 PostgreSQL / Redis / Qdrant
4. 跑 Alembic 数据库迁移
5. 启动 FastAPI 后端
6. 安装前端依赖
7. 启动前端开发服务器
8. 验证前后端连通

---

## 5. 详细实施步骤

### 步骤 1：确认 conda 环境

如果环境还没有创建：

```powershell
conda create -n rag_sec_phase1 python=3.11 -y
```

如果环境已经存在，可以直接跳过创建步骤。

验证环境是否存在：

```powershell
conda env list
```

预期看到：

```text
rag_sec_phase1
```

### 步骤 2：进入项目目录

```powershell
cd D:\Code_MyProject\RAG_Sec
```

### 步骤 3：安装后端依赖

优先使用项目定义安装：

```powershell
conda run -n rag_sec_phase1 pip install -e ".[test]"
```

如果安装后发现 `alembic`、`uvicorn`、`sqlalchemy` 等模块缺失，再补装关键依赖：

```powershell
conda run -n rag_sec_phase1 pip install alembic sqlalchemy psycopg2-binary pydantic pydantic-settings fastapi uvicorn redis celery qdrant-client httpx python-multipart PyMuPDF sentence-transformers torch pytest pytest-asyncio
```

### 步骤 4：准备环境变量

先从示例文件复制：

```powershell
Copy-Item .env.example .env
```

说明：

- 根目录 `.env` 供 Alembic / 本地命令使用
- 本地从 `backend/` 启动 `uvicorn` 时，项目对工作目录敏感
- 如果后端启动时报配置问题，可以把同样的 `.env` 再复制一份到 `backend/.env`

可选命令：

```powershell
Copy-Item .env.example backend\.env
```

### 步骤 5：启动基础设施

在项目根目录执行：

```powershell
docker compose up -d postgres redis qdrant
```

预期容器启动成功：

- cybersec-postgres
- cybersec-redis
- cybersec-qdrant

检查状态：

```powershell
docker compose ps
```

### 步骤 6：执行数据库迁移

在项目根目录执行：

```powershell
conda run -n rag_sec_phase1 cmd /c "cd /d D:\Code_MyProject\RAG_Sec && alembic -c backend\alembic.ini upgrade head"
```

这是当前项目在 Windows 下验证通过的迁移方式。

### 步骤 7：启动 FastAPI 后端

在 PowerShell 执行：

```powershell
conda run -n rag_sec_phase1 cmd /c "cd /d D:\Code_MyProject\RAG_Sec\backend && uvicorn app.main:app --reload --host 0.0.0.0 --port 8000"
```

如果你希望持续查看日志，就保持这个窗口不要关闭。

### 步骤 8：安装前端依赖

在新终端执行：

```powershell
cd D:\Code_MyProject\RAG_Sec\frontend
npm install
```

### 步骤 9：启动前端开发服务器

在前端目录执行：

```powershell
npm run dev
```

前端会在 `http://localhost:5173` 启动。

## 10. 常见问题处理

### 问题 1：No module named alembic

原因：

项目依赖没有完整安装到 `rag_sec_phase1`。

处理：

```powershell
conda run -n rag_sec_phase1 pip install alembic sqlalchemy
```

### 问题 2：`Path doesn't exist: backend\alembic`

原因：

你在 `backend/` 目录里直接执行了 `alembic upgrade head`，而当前 `script_location` 是按项目根目录解析的。

处理：

```powershell
conda run -n rag_sec_phase1 cmd /c "cd /d D:\Code_MyProject\RAG_Sec && alembic -c backend\alembic.ini upgrade head"
```

### 问题 3：`app.routes` 看起来只有少量路由

原因：

当前 FastAPI 0.139.0 环境里，`include_router()` 之后 `app.routes` 中会保留 `_IncludedRouter`，不再只表现为传统的 `APIRoute` 列表。

处理：

不要只用下面这种方式判断：

```python
isinstance(route, APIRoute)
```

应改为结合以下方式确认：

- `/docs`
- `/openapi.json`
- `TestClient(app)` 发真实请求

### 问题 4：杀毒软件误删 `safety_guard.py`

处理：

- 先从隔离区恢复文件
- 再把 `D:\Code_MyProject\RAG_Sec\backend\app\services\` 加白名单

### 问题 5：前端 Dashboard 显示 `Failed to fetch`

原因：

通常有以下几种可能：

1. Docker Desktop 没启动，导致基础设施没起来
2. 后端没启动或启动失败
3. 后端启动了但 `/api/v1/health/ready` 返回异常
4. 前端代理配置不正确

排查顺序：

1. 确认 Docker Desktop 已启动：`docker version`
2. 确认基础设施已启动：`docker compose ps`
3. 确认后端可访问：`http://localhost:8000/health`
4. 确认后端就绪：`http://localhost:8000/api/v1/health/ready`
5. 确认前端代理配置正确（已在 [vite.config.ts](file:///d:/Code_MyProject/RAG_Sec/frontend/vite.config.ts) 中配置）

### 问题 6：前端端口被占用

原因：

端口 5173 已被其他服务占用。

处理：

在 `frontend/vite.config.ts` 中修改端口：

```typescript
server: {
  port: 5174,
},
```

当前项目已经具备：

- 可启动的 FastAPI 后端
- 可用的 PostgreSQL / Redis / Qdrant readiness 检查
- 可运行的 Alembic 迁移链路
- 已可见的 upload / documents / query / eval / health 接口
- 可启动的 React + TypeScript + Vite 前端
- 已配置的前端代理，可转发请求到后端

但要注意：

- 当前 FastAPI 版本下，路由是否可用不能只通过 `app.routes` 的 `APIRoute` 过滤结果来判断

- 前端依赖后端运行，启动顺序必须是：基础设施 → 后端 → 前端
