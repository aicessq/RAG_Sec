1. 一句话定义当前项目状态

面试里一个非常关键的能力，是能把“当前阶段到底完成到哪里”讲得既准确又不过度。

推荐表述：
这是一个面向网络安全知识资料的 RAG 后端项目，当前已经完成到 Phase 6。系统不仅能把 child chunk 建好向量索引和关键词索引，还已经能接收 query，同时做 Qdrant 向量召回和 PostgreSQL FTS 召回，再通过 RRF 融合返回 top_k 相关 child chunks。但当前仍未进入 query 理解、安全边界、答案生成和引用校验阶段。

2. Phase 6 相比 Phase 5 升级了什么

面试官更关注“系统能力发生了什么本质变化”，而不仅仅是“你多写了一个 API”。

Phase 4 已完成

解决结构化切分、parent-child 关系、chunk_hash 和 chunk 落库问题。

Phase 5 已完成

解决本地 embedding / reranker 封装、Qdrant / FTS 索引建立问题。

Phase 6 当前重点

解决“输入问题后，系统如何把相关 child chunk 实际搜出来并统一返回”问题。

本质升级

  • 系统从“索引已经建好”升级为“第一次真正可检索”。
  • 项目第一次具备“输入 query → 返回相关 chunks”的完整基础闭环。
  • Phase 7 / 8 的 query 理解与答案生成终于有了真实可用的召回底座。

4. 检索链路怎么讲清楚

真正体现理解深度的，不是“我做了一个 retrieve API”，而是你能把检索闭环讲清楚。

推荐你背下来的处理顺序

客户端发送 query
  -> /api/v1/query/retrieve 接收 query / top_k / filters / debug
  -> MetadataFilter 规范化显式过滤条件
  -> embedding_service 对 query 向量化
  -> vector_store.search 在 Qdrant 中召回 child chunk
  -> keyword_store.search 在 PostgreSQL FTS 中召回 child chunk
  -> fusion.reciprocal_rank_fusion 做 RRF 融合
  -> 截取最终 top_k 结果
  -> 若 debug=true，额外返回 vector_results / keyword_results / fused_results

为什么 Phase 6 很关键

因为从这一阶段开始，系统第一次拥有了真正可用的检索能力。没有 Phase 6，Phase 5 的索引虽然建好了，但系统仍然只是“有索引，没有召回链路”。

为什么当前结果仍然只返回 child chunk

因为当前阶段的目标是“检索主单元召回”。child 更适合精细召回，parent 更适合后续命中后的上下文回填。所以 Phase 6 仍然不把 parent 放进主结果集。

5. 关键设计点为什么这样做

面试里最常见的追问，几乎都在“为什么”上。

1）为什么向量检索和关键词检索必须并行存在？

因为混合检索的核心就是两路互补。向量检索擅长语义相关，FTS 擅长法规编号、标准编号、英文术语、CVE 等精确文本信号。缺一路，召回能力都会明显失衡。

2）为什么 metadata filter 现在只做显式过滤，不做智能推断？

因为 Phase 6 的职责是“过滤规则正确执行”，而不是“从用户自然语言自动推断过滤意图”。后者属于 Phase 7 的 query 理解能力，如果现在提前做会直接越界。

3）为什么要用 RRF，而不是现在就上 reranker？

因为 RRF 是最基础、最稳定的多路结果融合方式，适合当前先把召回闭环打通。reranker 虽然在 Phase 5 已经封装，但正式进入查询链路会把当前阶段复杂度拉高，也越过了既定边界。

4）为什么 `/query/retrieve` 被定义成调试接口？

因为当前阶段的目标是验证“系统能不能把相关 chunk 召回出来”，而不是向用户返回最终答案。调试接口更强调检索明细、分路结果和融合结果，便于开发阶段观察质量。

5）为什么默认过滤规则必须现在就正确？

因为默认检索范围一旦错了，后续版本切换、软删除、历史版本查询都会出现语义错误。当前就必须保证 active document、active version、active chunk、current version only 的默认规则成立。

6）为什么现在完成了检索，还不能说“RAG 问答已经完成”？

因为当前只完成了召回层，还没有做 safety_guard、intent_classifier、query rewrite、rerank 主链路、answer generation 和 citation checker。所以当前完成只能理解为“Phase 6 阶段目标完成”。

6. 面试官高频追问与答题思路

下面这些问题，就是你讲到当前阶段时大概率会被追问的点。

Q1：你们现在已经能做检索了吗？
A：能做基础检索了。当前已经可以把 query 同时送到向量检索和关键词检索，再通过 RRF 融合返回 top_k child chunks，但还没有进入完整问答阶段。
Q2：为什么不能只做向量检索？
A：因为网络安全领域有很多强关键词场景，比如法规条号、标准编号、英文术语、漏洞编号。只做向量检索，精确命中这些信号会明显不稳定，所以必须保留 FTS 一路。
Q3：为什么当前 metadata filter 不是从自然语言自动识别的？
A：因为 Phase 6 只实现“显式 filter 执行”，不做 query 理解。把过滤意图从自然语言里自动提取出来，是 Phase 7 的范围。
Q4：为什么 RRF 先上，reranker 反而还没接进来？
A：因为 RRF 足够轻量，能先把两路检索结果统一起来；reranker 接入会让当前阶段复杂度明显增加，更适合在后续更完整的查询编排阶段加入。
Q5：为什么检索结果里不直接返回 parent chunk？
A：因为当前检索主单元仍然是 child chunk。parent chunk 不是拿来直接召回排序的，而是给后续命中后的上下文回填做准备。
Q6：你们现在的 retrieve API 是给终端用户直接用的吗？
A：当前更偏调试接口。它主要用于观察 vector、keyword、fused 和 final results，帮助验证召回链路是否正常，不是最终问答接口。

9. 你该怎么口述这个项目

最后给你一个适合面试场景的口述模板。

我做的是一个网络安全领域 RAG 知识库后端项目。这个项目是按 Phase 逐步推进的：先完成工程骨架和基础设施联通，再完成数据库地基、上传入口、解析清洗、结构化切分和索引建立。当前推进到 Phase 6，核心是让系统第一次具备真正的基础检索能力。现在系统已经能对 query 做 embedding，同时执行 Qdrant 向量检索和 PostgreSQL FTS 检索，再通过 RRF 融合返回 top_k child chunks，并支持基础 metadata filter。这样虽然还没有进入 query 理解和答案生成阶段，但已经把后续问答系统最关键的召回底座准备好了。

如果你把上面这段讲顺，再能回答“为什么要保留 FTS”“为什么 Phase 6 只做显式 filter”“为什么先上 RRF 而不是 reranker”“为什么现在可检索还不等于可问答”，基本就能把当前阶段讲得很扎实了。
