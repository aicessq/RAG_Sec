启动项目并完成第一次验证

本课目标：你能把依赖拉起来，并知道哪两个健康检查分别证明“进程活着”和“依赖通了”。

Tangible win：你能解释 GET /health 与 GET /api/v1/health/ready 的区别，并说出本地跑 backend 时 .env 该放哪。

1. 环境约束（先记住）

  • Python 工作必须在项目专用环境（conda rag_sec_phase1 或 .venv），不要用全局 Python。
  • Settings 从当前工作目录读 .env。从 backend/ 起 uvicorn 时，需要 backend/.env。
  • Docker Compose 直接注入环境变量，可规避 cwd 问题；backend 与 worker 必须共享同一 STORAGE_ROOT 卷。

2. 最小启动路径

# 根目录：基础设施 + worker（入库需要）
docker compose up -d postgres redis qdrant worker

# 或本地 backend（在 backend/）
conda activate rag_sec_phase1   # 或 .venv
cd backend
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000

前端（另开终端）：

cd frontend
cp .env.example .env   # VITE_API_BASE_URL=http://localhost:8000
npm install
npm run dev            # http://localhost:5173

3. 验证清单

  • GET /health → 进程存活（liveness）
  • GET /api/v1/health/ready → PostgreSQL / Redis / Qdrant 就绪（readiness）
  • Swagger：http://localhost:8000/docs
  • 有代理时：本地测试设 NO_PROXY=localhost,127.0.0.1，否则可能假 502

4. 测试怎么跑

# 仓库根目录
pytest                              # 默认排除 integration
pytest backend/tests/test_health.py
pytest backend/tests/test_health.py::test_health_returns_ok
pytest -m integration               # 需要真 PG/Redis/Qdrant，失败不 skip

5. 练习

先不看答案：

  1. 只起了 backend、没起 postgres，哪个接口更可能先红？
  2. 为什么 upload 后任务一直 queued，却不该先怀疑 FastAPI 路由？
  3. 本地从 backend/ 启动，却把 .env 只放在仓库根目录，会怎样？
展开参考答案
  1. /api/v1/health/ready（依赖探测）；/health 仍可能 ok。
  2. 入库靠 Celery worker + Redis broker；先查 worker 是否在跑、是否同网络同 storage。
  3. 配置可能读不到，数据库/模型路径用默认值或报错；应放 backend/.env 或显式注入环境变量。
