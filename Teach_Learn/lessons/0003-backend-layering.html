后端分层：API / Service / Worker

本课目标：看到一个需求时，你能判断该改路由、服务，还是异步 worker——而不是在三个目录里同时“乱改”。

Tangible win：能用一句话说明为什么 api/ 必须保持薄，以及 QueryService 在链路里的角色。

1. 三层各自负责什么

api/

HTTP 边界：参数校验、调用 service、把异常翻译成统一错误响应。不写主流程。

services/

业务编排：upload、retrieve、answer、eval、update。外部模型调用也封装在这里。

workers/

Celery 异步执行：ingest / replace 等长任务，更新 ingest_tasks 与索引。

2. 请求怎么穿层

HTTP
  → main.py 注册的 router（注意：本项目显式展开 router，不依赖聚合 include）
  → api/*.py 薄处理
  → services/* 主逻辑
  → models / db 持久化
  → 外部：PG / Redis / Qdrant / 本地 embedding / LLM API

查询链路的编排中心是 services/query_service.py：prepare() 与 answer() 把 safety → rewrite → retrieve → generate 串起来；api/query.py 只做入参出参。

3. 同步 vs 异步怎么选

  • 同步 service：查询改写、检索、生成答案——用户在等结果。
  • 异步 worker：解析 PDF、切块、embedding、写索引——耗时长，用 task_id 查进度。

4. 练习

先不看答案：

  1. “给 /query/answer 增加一个 debug 字段返回 rewritten_query”，主要改哪两层？
  2. “入库失败要把更细的阶段写进 progress”，优先改哪里？
  3. 为什么不该在 api/upload.py 里直接调 PyMuPDF 解析 PDF？
展开参考答案
  1. schema/response 与 api/query.py 出参；数据来自已有 QueryService，不必把逻辑塞进 route。
  2. workers/ingest_worker.py（以及它调用的 service），并更新 ingest_tasks；API 只读任务状态。
  3. 解析属于入库流水线，应在 worker/service；API 只负责接收文件与创建任务，否则超时且难测难复用。
