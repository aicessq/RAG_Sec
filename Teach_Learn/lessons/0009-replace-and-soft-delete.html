替换、增量更新与软删除

本课目标：你能解释“为什么不能全库重建”，以及 chunk_hash diff 如何决定 added / removed / unchanged。

Tangible win：能一句话说清“file_hash 快速判断 unchanged，chunk_hash 决定增量更新范围”。

1. 替换流程

replace API
  → 校验 file_hash（unchanged 则拒绝新建版本）
  → 创建新 version + replace task
  → 重新 parse / clean / chunk
  → 以 child chunk_hash 做 diff
  → added：重嵌索引
  → removed：三端停用（PG / Qdrant / FTS）
  → unchanged：复用旧向量
  → 切换 current_version_id

2. 为什么必须 chunk_hash diff？

  • 全库重建太慢、太贵。
  • 只对变化的 child 重算 embedding。
  • unchanged child 复用旧向量，但必须落新 DB 行（避免脏读）。

3. 软删除

soft delete：
  documents.status = deleted
  chunks.is_active = false
  Qdrant / FTS 可见性同步关闭

4. 练习

  1. 用户上传同一份 PDF，file_hash 相同，会发生什么？
  2. 为什么 soft delete 必须同步关闭 Qdrant 可见性？
  3. 你看到一个 chunk 的 is_active=false，但 Qdrant 仍可检索，这是什么问题？
展开参考答案
  1. 返回 file_unchanged，不创建新版本。
  2. 否则检索仍会命中已删除内容。
  3. 三端可见性不同步；需要修复 update_service 的 deactivate 逻辑。
