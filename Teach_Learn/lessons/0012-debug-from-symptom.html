从症状定位文件：调试方法论

本课目标：给你一个可复用的排查顺序——从用户可见症状反推 API → service → worker/存储，而不是全仓库搜索关键词碰运气。

Tangible win：面对任意一个功能 bug，你能写出“先看哪 2–3 个文件 + 验证哪一个接口/表字段”。

1. 固定排查顺序

1. 复现路径：哪个页面/接口？同步还是异步？
2. API 层：请求进没进、错误码是不是统一 error 结构
3. Service 层：主流程哪一步的输入输出异常
4. 若异步：worker 日志 + ingest_tasks.status/error_message
5. 持久化/可见性：PG 记录、Qdrant payload、FTS is_active 是否对齐
6. 仅当证据不足时，再看 prompt / 模型配置

2. 症状 → 优先文件速查

上传后一直 queued

upload_service → Celery / ingest_worker → Redis → 共享 storage

能入库但检索为空

chunk 是否 child+active；Qdrant/FTS 是否写入；四重可见性过滤

改写怪异 / 误拒答

safety_guard → intent_classifier → query_rewriter + 对应 prompts

答案胡编 / 引用假页码

answer_generator + citation_checker；先用 retrieve 看证据是否对

替换后仍搜到旧文

update_service：chunk diff、deactivate、current_version_id、三端可见性

评测指标异常

eval_service + golden 样本期望字段；确认跑的是真实 query 链路

3. 调试接口比“直接看答案”更高效

  • /query/rewrite：看安全、意图、改写、filter
  • /query/retrieve：看向量/关键词/融合结果
  • /query/answer：最后才看生成质量
  • /documents/tasks/{id}：看入库阶段

4. 综合练习

对每个症状，写出：优先文件 + 验证手段

  1. 前端 Answer 返回 502，但 curl localhost:8000/health 正常。
  2. 同一文档 replace 后，file 变了但 embedding 调用次数几乎为 0。
  3. 攻击性提问仍给出利用步骤。
展开参考答案
  1. 可能代理干扰或前端 base URL 指错；查 VITE_API_BASE_URL、NO_PROXY、CORS；用 Swagger 直打 /query/answer 排除前端。
  2. 可能大量 child chunk_hash 未变，走了 unchanged 复用——属预期；用 diff 统计 added 数量与 update_service 日志确认。若内容大变却 0 embedding，查 hash 规范化是否过度。
  3. safety_guard（规则+LLM）与 answer 是否在 refuse/redirect 后仍生成；查 query_log 的 safety_action 与 API 短路逻辑。
