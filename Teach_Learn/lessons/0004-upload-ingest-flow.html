上传与异步入库链路

本课目标：你能从 POST /documents/upload 一路跟到 Celery worker 写完索引，并说出每个阶段“写了什么库”。

Tangible win：能区分 upload 同步返回的 task_id 与后台真正完成的 ingest_task.status=completed。

1. 端到端顺序

multipart 上传
  → 校验扩展名 / MIME / 大小
  → 算 file_hash，原始文件落 storage
  → 创建 document + version_no=1 + ingest_task(queued)
  → 投递 Celery
  → parse → clean → parent/child chunk 落 PG
  → 仅 child：embedding → Qdrant + FTS
  → task completed

2. 模块分工

  • api/upload.py：HTTP 入口
  • upload_service.py：校验、存盘、建记录、派发任务
  • ingest_worker.py：异步编排
  • parser_service / cleaner_service / chunk_service
  • index_service / embedding_service / vector_store / keyword_store

3. 必须记住的规则

  • upload 只建新 document，不能通过 upload 挂到旧 document；新版本用 replace。
  • 任务状态 DB + Redis 双写；接口查任务以 DB 为准。
  • backend 与 worker 必须共享同一 storage 卷，否则 worker 找不到文件。

4. 练习

  1. 上传接口立刻返回 200 且带 task_id，是否代表已经可被检索？
  2. 用户想“更新已有法规 PDF”，应调哪个接口而不是 upload？
  3. 解析失败时，你期望在哪张表看到什么字段？
展开参考答案
  1. 否。只代表已入队；可检索需 task completed 且 child 已索引。
  2. POST /api/v1/documents/{id}/replace。
  3. ingest_tasks：status=failed，并有 error_message / finished_at。
